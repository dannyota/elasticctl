## Confirmed findings

### V052-001: Recorder cleanup advances past failed content dependencies

- Severity: Medium, release-blocking
- Location: `xtask/src/main.rs:2170`, `xtask/src/main.rs:2242`, and
  `xtask/src/main.rs:2294`
- Violated specification: `docs/specs/elasticctl-content-design.md:599` says,
  "It deletes data views only after every dashboard delete and the verified
  default restore succeed, and deletes the marker index only after every
  data-view delete succeeds. A failed prerequisite retains its dependents for
  the Drop retry."
- Failure scenario: `data_view_cleanup_safe` is cleared only when default
  restoration fails. If a dashboard ownership check, delete, or post-delete
  verification fails, cleanup records the error but still deletes the owned
  companion data view. If a data-view ownership check, delete, or post-delete
  verification fails, cleanup still deletes the owned backing index. The first
  path can leave a retained dashboard with a missing reference. The second can
  leave a retained data view whose index no longer exists.
- Smallest fix: gate all data-view deletion on both successful default
  restoration and zero remaining owned dashboards. After the data-view loop,
  gate index deletion on zero remaining owned data views. Preserve ownership
  on every failed prerequisite so `Drop` can retry.
- Exact regression tests: add
  `dashboard_cleanup_failure_retains_data_views_and_their_index` and
  `data_view_cleanup_failure_retains_its_index` to the `xtask/src/main.rs`
  test module.
- Fix: `c21418b` (`Preserve recorder content cleanup dependencies`). Both
  regressions and all 99 xtask tests pass after the fix. The final scope checks
  also pass.

## Rejected findings

The following attacks did not produce a defect:

| Attack | Evidence and disposition |
| --- | --- |
| Selector ambiguity | Data-view ids win over names; duplicate exact names fail. Dashboard ids win over titles; duplicate exact titles list every matching id. API and CLI resolution tests pass. |
| Empty mutation | Clap requires data-view delete targets; dashboard delete rejects an empty vector before context construction; both portable imports reject empty artifacts. |
| Dry-run network writes | Guarded command tests prove no mutation request is sent. The no-flag data-view import preview is intentionally local under the v0.5.0 plan; conflict modes and every apply use authenticated preflight. |
| File re-read after guard | Import plans retain parsed specs or exact NDJSON. Tests mutate the source after planning and prove apply uses the retained body. |
| Import create/replace race | Data-view and dashboard apply paths re-read each stable id immediately before the write and reject appeared, disappeared, or changed objects. |
| Partial failure exit | Typed failed and lossy rows make the CLI exit nonzero while preserving every per-object outcome. CLI integration tests pass. |
| Lossy 2xx | Dashboard PUT response bodies are checked as recursive supersets of submitted data. Dropped values are reported with `applied: true` and make the command fail. |
| Warning-bearing export | Typed dashboard export rejects every GET warning and directs the user to opaque bundle export. |
| Opaque byte change | Bundle planning retains the exact UTF-8 NDJSON string. Export returns raw bytes and import uploads the retained bytes without JSON rewriting. |
| Trailer misclassification | The bundle scanner accepts at most one validated export-details trailer and requires it to be the last nonempty line. Object lines still require string `type` and `id`. |
| Referenced/default delete | Direct data-view delete refuses references and current-default membership. Replacement rechecks reference and default snapshots before the swap. |
| Default partial failure | After a successful swap/delete, failed default reads or writes report a partial failure instead of claiming the operation was unapplied. |
| 204 decode | Dashboard delete accepts only the transport's null representation of an empty success body. Data-view delete accepts null or exact `acknowledged: true`. |
| Feature floor | `Feature::Dashboards` is available from 9.5.1 on every flavor and rejects lower or unreadable versions. Capability tests pass. |
| Baseline default drift | Live and controller baselines compare the exact optional default id. Marker or whitespace-only live baselines are refused before mutation. |
| Unscoped fixture request | Recorder dashboard export names one marker dashboard, dashboard search uses an exact marker query, and fixture checks reject scope and scrub violations. |
| Secret or identity leakage | Recorder errors use classified static summaries; fixtures and public reports pass the repository leak scanners. |

The cleanup-after-decode-failure attack produced V052-001: error collection was
safe, but its dependent-delete gates were incomplete.

## Disposition

V052-001 is fixed by `c21418b` through `docs/plans/v0.5.2-review.md`. The
regressions prove that a failed dashboard retains data views and their index,
and that a failed data view retains its index. The bounded review is closed;
no finding is reserved for a later 0.5 release.
