All of M1 to M8 match the design. M3 confirms that a target deleted after the
last check shows as `requested > total` and is reported as failed. M8 shows
that the 20-target cap fits the 30-second deadline with room to spare.

M9: on Serverless 9.7.0 an organization-level Cloud API key authenticates,
realm `_cloud_api_key`, and enabled a disabled marker rule: one rule
succeeded, none failed or skipped, and a read-back showed it enabled. This
reverses the failure recorded on 2026-08-13 (shared design section 7.2). The
first M9 run, at `f03048c`, classified the outcome without the read-back; the
rerun at `10e3d28`, from `04:22:28Z` to `04:28:25Z`, measured it as above. On
Hosted `_authenticate` answers 401 for the same key. The planner refuses realm
`_cloud_api_key` on every flavor before anyone is asked, as policy: the key's
reach spans the organization and `_authenticate` does not show its role
scope, so a plan cannot show what the key may do (mutation design section
5.2).

M13: a rule created disabled has no API key; enabling it gives it the
enabler's key. After that, a disable and an enable by another credential both
kept the existing owner. The consent note now states both cases (mutation
design section 6.1, decision D34).

## Product client

Claude Code 2.1.322 ran interactively against the lab on protocol
`2026-07-28`, with the server behind `scripts/mcp-stdio-shim.sh`. Claude Code
ran with `--permission-mode default`, because the account's settings start
sessions in bypass-permissions mode, which skips the permission card.
`plan_apply` was not allowed in advance.

| Fact | Accept | Decline |
| --- | --- | --- |
| Order | Permission card, then the form | Same |
| `plan_apply` sent before the card was allowed | No | No |
| Form boolean at start | `false` | `false` |
| Second round carried `inputResponses` and `requestState` | Yes, `accept` with `apply: true` | Yes, `decline` |
| Result | Applied, 1 updated | `plan_declined` |
| Rule state after, read through the CLI | Changed | Unchanged |
| Audit lines | Created, requested, confirmed, started, finished | Created, requested, declined, closed |

Measurement M10 failed on the first run, from `02:43:22Z` to `02:49:15Z`: the
form showed only the first three lines of the twelve-line message and
collapsed the rest, with no key to expand it, so the person saw the target
but not the change. The consent text now puts the action with its count, the
target, and the first affected object on those three lines (decision D33).
The rerun, from `03:27:12Z` to `03:29:03Z` on the same tree as `79d947d`,
showed exactly those three lines, and both scenarios passed again. After the
first decline the model told the person the plan stayed open; the decline
message now says the plan is closed, and after the rerun's decline the model
said so. Both runs had no unparseable frame and no JSON-RPC error.

## Cleanup and evidence limits

Every run ended with the baseline it started from. Closed marker alerts are
the accepted residue of the contract. The lab was destroyed after the last
run, leaving no lab container, volume, or network.

- The contract's harness answers the form itself. That is test consent: it
  proves the protocol mechanics, not that a product client asks a person.
  The product client run does that, for one client on one path.
- M13 ran only on the 9.5.1 lab, where a second credential can be made.
- The product client ran on the lab. From 2026-11-11, by owner decision,
  model-driven clients run against the test-only Hosted deployment instead.
- Raw results, frames, and pane captures stay private. No live request
  capture is claimed.
