# 0.10 value-list research

Research date: 2026-11-12. Baseline: `dev-0.9.3` at `0f39d6a`, workspace
version 0.9.2.
This is planning evidence. No 0.10 code or design exists. Nothing below was
measured live; the live rows are listed for a teammate to run on Serverless,
Hosted, and the self-managed lab before the current trial targets end.

## Recommendation

Manage Elastic Security value lists as code in 0.10, the way 0.2 added
exception lists: a new command group and a closure in the state mirror.

1. Identity is the caller-supplied list `id` inside the profile's space. Item
   `id`, `_version`, `tie_breaker_id`, `version`, and timestamps are volatile.
   An item is its value, after Kibana's read-back form (V4).
2. Manage four types: `keyword`, `ip`, `ip_range`, `text`. Refuse the other
   19 API types by name.
3. `state pull` also writes every value list a mirrored exception item
   references: `value-lists/<id>.yaml` holds `id`, `type`, `name`,
   `description`, and `meta`; `value-lists/<id>.txt` holds the values, one per
   line, sorted and unique. `state push` creates missing containers, updates
   name, description, and meta, and reconciles values exactly, deletes
   included. It applies value lists first, then exception containers, items,
   and rules. It never deletes a value-list container.
4. Commands: `value-lists list | get | validate | export | import | delete |
   init`. Every remote mutation is a dry run by default, applies with `--yes`,
   and prints profile, host, and space.
5. Apply reads back. After a write, the list is exported again and compared
   with the plan, because `_import` returns no counts and can drop values
   without an error (source, V5).

Leave out:

- `deleteReferences=true`: Kibana rewrites every referencing exception item
  and keeps only its other list entries, which widens the exception (source).
- `ignoreReferences=true`: it leaves dangling references; with `is not in
  list` that may suppress every event that has the field (source, V7).
- The other 19 types: the UI offers four, and the detection engine's inline
  path processes only `keyword`, `ip`, and `ip_range`.
- Item `meta`: export drops it and import cannot set it.
- `serializer` and `deserializer`: removed in 9.2.7, 9.3.2, and 9.4.0, and
  ignored with a warning header on every target.
- `_import` without `list_id`: the list `id` becomes the upload's file name.
- `DELETE /api/lists/index`: it drops every list in the space.
- Value lists as an indicator match index: a rule feature, not list content.
- MCP tools: keep 0.10.0 to the CLI and state contract (owner decision 9).
- Cross-space copy: the profile's space only, as for every other object.

## Existing elasticctl code and contracts

- Scope deferred value-list content in 0.1
  ([01-scope.md:13-15](../specs/elasticctl-design/01-scope.md)).
- Spec 7.7 measured the data streams on Serverless 9.6.0 and states that list
  content "is data rather than configuration and is not managed here"
  ([07-verified-api-facts.md:237, 301-306](../specs/elasticctl-design/07-verified-api-facts.md)).
  0.10 reverses that sentence and must update it in the same commit.
- `ValueListRef` holds `id` alone, and its comment says a value list has no
  namespace (`crates/elasticctl-api/src/exceptions/value_lists.rs:6-13`).
  True for the API, but the data streams are per space.
- `value_lists_bootstrapped` treats 404 as absent and requires both booleans
  (`value_lists.rs:21-38`). `value_list_exists` uses the status only
  (`value_lists.rs:51-57`).
- `doctor` warns `value_list_index` when absent and names `POST
  /api/lists/index` (`crates/elasticctl-api/src/health.rs:191-211`, called at
  `:256`). The v0.9.1 findings record that warning on both Cloud targets
  ([v0.9.1-findings.md:22](../conformance/v0.9.1-findings.md)).
- `state push` collects value-list ids only from items in the active closure
  (`crates/elasticctl-api/src/state/push.rs:75-79`) and adds a preview line
  per absent list (`push.rs:172-193`). It does not refuse; the apply
  proceeds. `value_list_refs` reads `list.id` and ignores `list.type`
  (`state/push/references.rs:52-94`). Tests:
  `crates/elasticctl-api/tests/state.rs:1385-1600`.
- All three recorded fixtures answer 404 "data stream .lists-default and data
  stream .items-default does not exist":
  `tests/fixtures/{traditional-9.5.1,ech-9.5.2,serverless-9.7.0}/lists_index.json`,
  from `xtask/src/recorder/mod.rs:103-116`. Every value-list probe therefore
  starts with a space-wide bootstrap (V2).
- `read_mirror` reads only `rules/` and `exceptions/` and classifies YAML
  entries by `rule_id`, `item_id`, then `list_id`
  (`crates/elasticctl-api/src/state/mirror.rs:18-56, 213-232`). A value-list
  item carries `list_id`, so value lists need their own directory and
  decoder. A 0.9 binary ignores `value-lists/` and pushes without it.
- Spec 5.4 sets the closure, the fixed apply order, "Containers and rules are
  never deleted", and exact item reconciliation
  ([05-state-engine.md:202, 223, 238](../specs/elasticctl-design/05-state-engine.md)).
  Value lists fit the same reasoning: content is written in full.
- `exceptions` has no `create` verb because a file is better than flags
  ([04-command-surface.md:40-43](../specs/elasticctl-design/04-command-surface.md)).
  The same holds for value lists.
- A new `value_lists` block in `diff` narrows `clean`, which 11.1 treats as
  a break, as it did for 0.2's `exceptions` block
  ([11-versioning.md:153-159](../specs/elasticctl-design/11-versioning.md)).
- Live objects carry the `elasticctl-live-` prefix and the
  `elasticctl-live-marker` tag
  ([live stacks](../../instructions/live-stacks.md)).
  Value lists have no tags, so the marker is the `id` prefix, the
  description `elasticctl-live-marker`, and `meta.marker`.

## Owner decisions needed

1. Command group name? Recommend `value-lists`. `lists` already means
   exception containers in code (`bundle.lists`) and docs.
2. Does `state pull` include referenced value-list content by default?
   Recommend yes. A mirror that references a list it cannot restore cannot be
   promoted, which is the tool's main use.
3. Mirror format for values? Recommend `value-lists/<id>.txt`, one value per
   line, sorted and unique, beside `<id>.yaml`. It diffs well in git and is
   Elastic's own import format.
4. Should push refuse when a referenced list is absent remotely and not in the
   mirror, or when its `type` differs from the entry's `list.type`? Recommend
   refuse. Today it is a preview line only, and a dangling `is not in list`
   may suppress every event (V7).
5. After V2 on the trial stacks, restore "not bootstrapped"? Recommend `DELETE
   /api/lists/index` only when V1 found the streams absent and
   `GET /api/lists/_find?per_page=1` reports `total: 0`. Runs must end at
   baseline.
6. Bootstrap? Recommend a guarded `value-lists init` that runs the
   `create-list-indices` flow; push never bootstraps. It is a space-wide
   change and should be asked for by name.
7. Types? Recommend `keyword`, `ip`, `ip_range`, `text` only. They are the
   documented UI types and the only ones exceptions use in practice.
8. Item reconciliation? Recommend exact, deletes included, as spec 5.4 does
   for exception items. Removing a value is how an exception narrows.
9. MCP? Recommend no value-list tools in 0.10.0 and read-only tools in a
   later 0.10 patch. Mutation would need a new 0.9 plan class.
10. A cap on large value diffs? Recommend none in 0.10.0: the guard shows adds
    and deletes per list. Revisit with V9 timings.

Owner answers, 2026-11-12: all ten as recommended. Decision 5 applies to
the two Cloud targets; the CI lab is fresh on every run.
