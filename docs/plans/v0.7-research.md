# 0.7 MCP research

Research date: 2026-09-05. Baseline: `d91edd1`, workspace version 0.6.2.
This is planning evidence. No MCP implementation or live MCP measurement exists yet.

## Recommendation

Build a stdio Model Context Protocol (MCP) adapter over the existing API
orchestration. Start with a small fixed tool set, expand read coverage in
0.7.1, and use 0.7.2 for broader interoperability evidence and confirmed fixes.
Each shipped version must pass its own safety, packaging, and live-read gates.

The [shared design](../specs/elasticctl-design.md) already assigns read-only
MCP to 0.7, task-shaped tools and resources/prompts to 0.8, and mutation
consent to 0.9. This proposal preserves those boundaries.

| The current protocol revision is 2026-07-28. It replaces the initialization handshake with self-contained requests and optional `server/discover`. | [Current specification](https://modelcontextprotocol.io/specification/2026-07-28), [release announcement](https://blog.modelcontextprotocol.io/posts/2026-07-28/) | Choose and test a protocol revision explicitly. A 2025 handshake example is not evidence of current compliance. |
| The later `rmcp-v3.2.0` tag declares stable 2026-07-28 support and legacy compatibility. Its manifest declares Rust 1.88 and Apache-2.0. | [Tagged README](https://github.com/modelcontextprotocol/rust-sdk/blob/rmcp-v3.2.0/README.md), [manifest](https://github.com/modelcontextprotocol/rust-sdk/blob/rmcp-v3.2.0/Cargo.toml) | Pin `rmcp = "=3.2.0"`; the workspace's Rust 1.97.1 meets its declared requirement. Test both current and legacy flows. |
| The SDK advertises all its known revisions by default. Legacy initialization negotiates a supported alternative when needed. | [Tagged server handler](https://github.com/modelcontextprotocol/rust-sdk/blob/rmcp-v3.2.0/crates/rmcp/src/handler/server.rs), [legacy lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle#version-negotiation) | Override the supported set with two revisions. Reject unsupported current metadata; configure 2025-11-25 as the legacy fallback. |
| The SDK has an open report of an unbounded stdio input buffer. | [SDK issue 1030](https://github.com/modelcontextprotocol/rust-sdk/issues/1030) | Bound each input line before the SDK can buffer or parse it. |
| stdio carries newline-delimited JSON-RPC. stdout is reserved for protocol messages. | [stdio transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio) | Branch into the server before the CLI renderer and keep diagnostics off stdout. |
| Tools have input schemas, optional output schemas, structured results, and separate protocol and tool errors. Tool annotations are hints. | [Tools specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) | Use explicit schemas and executable admission checks; `readOnlyHint` cannot enforce read-only behavior. |
| `splunkctl` reflects its Click tree and exposes progressive discovery and a generic runner. | [Sibling project](https://github.com/dannyota/splunkctl#agent-integration-mcp) | Reuse the operator contracts, while following elasticctl's explicit typed API boundary. A generic runner would expose more than the 0.7 scope. |
| Synchronous ES\|QL uses `POST /_query` and requires index read privileges. | [Elastic ES\|QL API](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-esql-query) | HTTP POST alone does not distinguish a read from a mutation. |
| ES\|QL `COMPLETION` can send a request to an inference endpoint for each row. | [Elastic COMPLETION command](https://www.elastic.co/docs/reference/query-languages/esql/commands/completion) | Arbitrary queries can cause downstream calls and costs. | Existing transport retries 429/5xx responses up to three attempts. | [Core transport](../../crates/elasticctl-core/src/transport.rs) | Give MCP query tools a single-attempt transport, including disabled reqwest retries, so one call does not repeat inference work automatically. |
| 0.6.2 has ten passing conformance contracts on each supported deployment flavor. | [Existing findings](../conformance/v0.6.2/findings.md) | Reuse existing route evidence, but measure the new MCP execution path separately. |
| The v0.6.2 release lists all seven target archives, checksums, installers, and source assets. | [v0.6.2 release](https://github.com/dannyota/elasticctl/releases/tag/v0.6.2), checked with `gh release view` | The current target matrix is proven. A new library changes packaging without requiring a third binary or new target. |

## Reuse map

These are existing Rust paths, not proposed interfaces. The adapter must use
orchestration entry points where they exist.

| Domain | API entry points | Result or boundary |
| --- | --- | --- |
| Stack | `health::info`, `health::doctor` | `InfoReport`, `DoctorReport`; doctor messages need a separate safe projection |
| Rules | `rules_ops::list`, `rules_ops::get_one` | `RuleListReport`, `Rule`; list currently collects the corpus |
| Prebuilt | `prebuilt::status` | `PrebuiltStatus` |
| Exceptions | `exceptions::list_op`, `exceptions::get_op` | `ListReport`, `ListDetail`; identity includes namespace |
| Alerts | `alerts_ops::list`, `alerts_ops::get_one` | `AlertList`, `AlertHit`; bounded POST search |
| Cases | `cases_ops::list`, `cases_ops::get_one` | `CaseList`, `Case`; omit raw flattened extras from the MCP projection |
| Data views | `data_views_ops::list_op`, `data_views_ops::get_op`, `data_views::get_default` | `DataViewList`, `DataView`, optional default id |
| Dashboards | `dashboards_ops::list_op`, `dashboards_ops::get_op` | `DashboardList`, `Dashboard` |
| Fleet agent policies | `fleet::agent_policy_ops::list_op`, `get_op` | Safe summaries/details, not raw policy maps |
| Fleet integrations | `fleet::integration_policy_ops::list_op`, `get_op` | Safe summaries/details; excludes vars and inputs |
| Search | `search::esql::run_sync`, `search::dsl::run_sync` | `EsqlResponse`, `DslPage`; transport types need explicit MCP serialization |

The source files live under `crates/elasticctl-api/src/`. CLI context and
rendering live under `crates/elasticctl-cli/src/`. Some API result types do
not derive `Serialize`; this is adapter work, not a reason to capture CLI stdout.

## Operations excluded from the first MCP surface

| Operation | Reason |
| --- | --- |
| `rules preview` | Creates preview alerts. |
| Async ES\|QL and DSL export | Creates async results or point-in-time search contexts and later deletes them. |
| `state pull` | Writes and replaces local files through a journal. |
| `state diff`, file validators, `@file` input | Give the model filesystem access; need a separate local-data design. |
| Export commands and dependency bundles | Bulk content and artifact delivery need explicit size and data-access contracts. |
| Config tools | Could enumerate unrelated profiles or expose local paths and credential metadata. |
| Mutation previews and all apply paths | Belong with the 0.9 consent design, even where a particular preview only reads. |
| Fleet setup or package installation | Read tooling must work against an already configured deployment or return a clear failure. |

The exclusions are scope choices. For example, an in-memory export can be a
read; it is not automatically a mutation because it uses POST.

## Evidence gaps

1. Compile the pinned SDK with only `server`, `macros`, and `transport-io`.
   Its tagged source supports the design, but this planning session did not
   build it. Verify current discovery, a direct metadata-bearing first call,
   legacy initialization, cancellation, and the bounded input wrapper.
2. Measure at least one real stdio client before 0.7.0 and a second independent
   client before 0.7.2. Record client version and negotiated protocol.
3. Verify the planned MCP projections and limits through existing fixtures and
   direct read-only calls on each supported flavor. Existing CLI evidence does
   not prove the new adapter.
4. Record how large rule, exception, and Fleet collections behave under a call
   deadline and response-body cap. Their current collectors can read more rows
   than the MCP result displays.

The Cloud trial ends 2026-09-08 at 08:56 UTC. Capture authorized read evidence
while available during implementation. If access expires first, keep that
flavor's measurement open and use a renewed test target. Never infer a pass,
lower a gate, or fabricate a report to meet the date.
