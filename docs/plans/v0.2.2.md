# elasticctl 0.2.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship 0.2.2 with locked dependency resolution in CI, proof against
the workspace's declared Rust version, the full CLI smoke suite on Windows,
and a credential-free package preflight before the release tag.

**Architecture:** Keep product behavior unchanged. Strengthen the existing CI
workflow, add a separate manually dispatched release-preflight workflow, and
make the maintainer procedure require both checks on the exact commit that is
tagged. Keep the generated cargo-dist release workflow unchanged.

**Tech Stack:** GitHub Actions, Cargo, Rust 1.97.1 and stable, actionlint,
cargo-dist, GitHub CLI.

## Global Constraints

- Limit 0.2.2 to CI, Windows test coverage, release preflight, version metadata,
  and the documents that define those contracts. Do not change runtime code or
  live API behavior.
- Use the committed `Cargo.lock` for every Cargo CI command that resolves or
  builds dependencies. `cargo fmt` has no `--locked` option.
- Keep the stable job. Add a separate job that reads `rust-version` from the
  root workspace manifest and uses that exact toolchain.
- Do not edit `.github/workflows/release.yml`; cargo-dist owns it, and the
  v0.2.1 matrix is already proved.
- Give the preflight workflow only `contents: read`. Do not pass a crates.io
  token and do not run `cargo publish` without `--dry-run`.
- A GitHub Release ends this plan. Do not publish 0.2.2 to crates.io without
  separate approval naming version 0.2.2.
- Do not run live tests. This patch does not change a live contract.
- Do not commit `.env`, `AGENTS.md`, target URLs, deployment identifiers,
  account data, credentials, locations, or live object content.
- Work sequentially on local `master`. Do not use a worktree or parallel
  workers for these overlapping workflow and release files.

## File Map

- `docs/specs/elasticctl-design.md`: normative 0.2.2 CI and preflight contract.
- `docs/releasing.md`: exact maintainer sequence before and after a tag.
- `.github/workflows/ci.yml`: locked stable job, declared-Rust job, and full
  Windows CLI test suite.
- `.github/workflows/release-preflight.yml`: manual, read-only publish dry run.
- `Cargo.toml`: workspace and internal dependency versions.
- `Cargo.lock`: all five workspace package versions.
- `crates/elasticctl-cli/tests/snapshots/snapshots_render__info_json.snap`:
  public version shown by `elasticctl info --json`.
- `CHANGELOG.md`: user-visible 0.2.2 release entry.

- [ ] **Step 2: Lock the stable job**

      - run: cargo test --locked --workspace

- [ ] **Step 3: Add the declared-Rust job**

Place it after `test` and before the Windows job:

```yaml
  declared-rust:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - name: Read declared Rust version
        id: rust_version
        shell: bash
        run: |
          version="$(sed -n 's/^rust-version = "\(.*\)"/\1/p' Cargo.toml)"
          test -n "$version"
          test "$(printf '%s\n' "$version" | wc -l)" -eq 1
          echo "version=$version" >> "$GITHUB_OUTPUT"
      - uses: dtolnay/rust-toolchain@stable
        with:
          toolchain: ${{ steps.rust_version.outputs.version }}
      - uses: Swatinem/rust-cache@v2
      - run: cargo check --locked --workspace --all-targets
```

The stable ref supports an explicit `toolchain` input. Reading the manifest
keeps the job aligned when the declared version changes.

- [ ] **Step 4: Validate the workflow and its command contract**
