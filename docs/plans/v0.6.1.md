# elasticctl 0.6.1 Fleet Integration Policies Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add complete Fleet integration-policy administration and portable transfer: list, get, validate, export, guarded import, and guarded delete over stable ids, with exact package dependency and secret checks.

**Architecture:** Keep `elasticctl-cli -> elasticctl-api -> elasticctl-core`. `-api` gains `fleet/integration_policies.rs` for the portable model and strict route wrappers, and `fleet/integration_policy_ops.rs` for paging, normalization, portability, parent/package preflight, planning, apply, and delete. The existing agent-policy module exposes one narrow parent snapshot helper. `-cli` adds `fleet integration-policies`; the recorder adds a marker integration lifecycle and reduces package metadata before fixtures are committed.

**Tech Stack:** Rust 2024 (stable), tokio + reqwest, serde/serde_json/serde_yaml_ng, clap, wiremock + assert_cmd + tempfile, xtask fixture recorder.

**Spec:** [`docs/specs/elasticctl-fleet-design.md`](../specs/elasticctl-fleet-design.md) sections 1-4, 6-15. Shared contracts are in [`docs/specs/elasticctl-design.md`](../specs/elasticctl-design.md). Fleet conformance and the bounded review patch are 0.6.2 and out of scope.

## Global Constraints

- Dependency direction is exactly `elasticctl-cli -> elasticctl-api -> elasticctl-core`; `clap` types never enter `-api` or `-core`.
- Integration-policy identity is the stored package-policy `id`. Exact `name` is selector fallback only. Resolution tries id first, then returns `not_found` or `conflict` for zero or multiple exact-name matches.
- Every Fleet route wrapper calls `transport.require_feature(Feature::FleetPolicies)` first. The feature keeps the existing 9.5.1 fixture-evidence floor.
- Portable files are JSON arrays by default and YAML sequences on request. They contain `IntegrationPolicySpec` values sorted by `id`.
- `IntegrationPolicySpec` requires non-empty `id`, `name`, `package.name`, and `package.version`; a non-empty, sorted, duplicate-free `policy_ids`; and object-shaped `inputs`. `description`, `namespace`, package-level `vars`, package-level `var_group_selections`, top-level `condition`, and `additional_datastreams_permissions` are optional. Package-owned input, stream, variable, and variable-group maps stay open. Unknown top-level fields are rejected.
- An omitted `namespace` inherits the parents' namespace. Planning requires all selected parents to have one equal namespace, fills that value into the effective desired spec, and reports `conflict` when the parent namespaces differ. An explicit namespace remains exact. Export always writes the stored namespace.
- List reads use `GET /api/fleet/package_policies?page=N&perPage=1000&sortField=created_at&sortOrder=asc&format=simplified`; single reads add `?format=simplified`. Paging metadata is strict. Sorting, case-insensitive id/name search, and limit truncation are local.
- Create sends the complete effective spec, including its `id`, to `POST /api/fleet/package_policies`. Replace sends the complete effective spec without `id` to `PUT /api/fleet/package_policies/{id}`. Neither sends top-level `enabled`, `force`, or `create_dataset_templates`.
- Normalization requires top-level `enabled: true` and removes it. It removes audit/revision fields, deprecated `policy_id`, active-space-only `spaceIds`, generated input and stream ids, compiled input/stream content, derived Elasticsearch privileges, registry-derived package fields, `agents`, and null/false platform fields named by the spec. It rejects unknown top-level fields rather than dropping them.
- A live integration is `unsupported` for portable export, overwrite, or delete when `is_managed` is true; a parent is platform-owned or protected; `output_id` or `cloud_connector_id` is non-null; `supports_agentless` or `supports_cloud_connector` is true; `spaceIds` names another space; top-level `enabled` is false; secret references exist; or an exact package definition declares any configured package, input, or stream variable secret.
- Overwrite never changes an existing integration's package coordinate. When the desired `package.name` or `package.version` differs from the live value for the same id, planning returns `unsupported` before any package-status, package-metadata, or mutation request.
- Parent checks use a narrow snapshot: `id`, `name`, `namespace`, `agents`, sorted attached integration ids, platform ownership, and protection. Parent output ids, sharing, and other agent-policy-only portability fields do not widen integration-policy refusal. An existing integration must appear in every parent named by its `policy_ids`; disagreement is a malformed `http` response. The attachment list is also a race snapshot.
- Package checks keep two facts separate. `GET /api/fleet/epm/packages/{name}` supplies installation status. `GET /api/fleet/epm/packages/{name}/{version}` supplies the exact registry definition used to classify secrets. Requested and returned name/version must match.
- Integration dependency checks accept exactly two package states: `installed` with one non-empty `installationInfo.version`, or `not_installed` with no installed version. Every other status and every contradictory status/version combination is a malformed `http` response and never permits a write.
- Planning groups artifacts by package name and rejects more than one requested version. The exact installed version is ready. An absent package is a planned `name@version` install performed implicitly by Fleet's create path. A different installed version is `conflict`. elasticctl never issues package install, upgrade, downgrade, uninstall, or rollback requests.
- After every create attempt that could install a missing package, apply re-reads package status even when the policy write failed. If the exact version became installed, it updates the shared package snapshot, reports the observed install once, and permits later rows using it. A different version or malformed read blocks only rows using that package. No package is rolled back.
- Offline `validate` checks artifact structure only. Export, import planning, and delete planning perform exact package metadata checks. Errors name sorted `policy-id:field.path` entries and never include secret values or secret-reference ids.
- Import reads and validates the whole file before configuration is consulted and never re-reads it. It rejects duplicate ids and duplicate names. Default conflicts refuse, `--skip-existing` omits existing ids, and `--overwrite` classifies create, replace, or unchanged. A name owned by another id always conflicts.
- Apply rechecks object identity/content, relevant name ownership, parent snapshots and agent counts, and package status immediately before each stable-id write. After decoded write success it GETs and normalizes the stored policy and requires exact equality with the effective desired spec. A post-write mismatch is failed with `applied: true`; earlier writes are not rolled back.
- Remote import planning rejects an empty effective integration `inputs` object before the guard when exact package metadata declares any inputs. Offline validation remains structural, and packages with no declared inputs may remain empty. Exported complete simplified inputs are the canonical round-trip form.
- `affected_agents` is the sum over the union of parent ids for every row whose mutation route returned decoded success, including rows that later fail post-write verification. An agent belongs to one parent, so parent-id deduplication prevents double counting.
- Delete rechecks the integration, every parent snapshot, and package status, then sends `DELETE /api/fleet/package_policies/{id}` without `force`. A missing target after preview is failed `not_found`; deletion never uninstalls a package.
- Every remote mutation previews by default and applies only with `--yes`, printing profile, host, and space through `guard::check`. The new guarded paths are `fleet integration-policies import` and `fleet integration-policies delete`.
- Get returns a sanitized `IntegrationPolicyDetail`: `id`, `name`, `namespace`, `description`, sorted `policy_ids`, exact `package`, `affected_agents`, and sorted `blocked_by`. It never returns inputs, variable values, secret references, audit identities, environment ids, or compiled content.
- Import reports `{applied, succeeded, unchanged, skipped, failed, total, affected_agents, package_installs}`. Delete reports `{applied, deleted, failed, total, affected_agents}`. A non-empty `failed` collection exits 1.
- Fixtures come from real traffic only. Recorder mutations use explicit `elasticctl-sample-*` ids/names and preflight those fixed ids as absent. Each session keeps an in-memory nonce, embeds it in parent and integration descriptions (the duplicate probe shares it), and claims ownership only after strict marker-state verification. After an ambiguous create error, an exact GET may claim cleanup only for the same nonce; another session's nonce is never deleted. Normal update preserves the nonce, and reducers map nonce-bearing descriptions to fixed public descriptions before writing fixtures. The recorder requires exact `system` to be preinstalled, never mutates package inventory, and retains the baseline only for exact-version ownership proof and unchanged-inventory audit. It deletes integrations before parents. Registry responses are reduced to the fields needed for status and secret classification before they enter public fixtures.
- Every integration-recorder marker POST, PUT, and DELETE is one-shot and redirect-free, including cleanup. Its HTTP client disables connection pooling and protocol-level retries. Redirects, transient responses, pooled-connection cancellation, protocol retry signals, and malformed successes do not trigger transport replay. Exact nonce-bound reads reconcile ambiguity, so a reused fixed id cannot be overwritten or deleted by a retry or redirect.
- Newly measured facts update `docs/specs/elasticctl-fleet-design.md` in the same commit as their fixtures. Claims that remain source-derived stay in section 15.2.
- Commit messages are plain imperative sentences with no prefixes, agent attribution, trailers, or generated-by text.
- Gates: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test -- --test-threads=6`, `cargo deny check advisories bans licenses sources`, `./scripts/check-packages.sh`, `./scripts/check-fixtures.sh`, `./scripts/check-conformance-reports.sh`.
- The workspace version stays `0.6.0`; release preparation performs the version bump to `0.6.1` and the locked publish dry run.

```rust
enum PackageDependencyState {
    Installed { version: String },
    NotInstalled,
}
```

`installed` without a version, `not_installed` with a version, `installing`, `failed`, and unknown statuses are `http`. None may reach a policy write.

The metadata decoder constructs keys as Fleet's simplified schema does: `<policy-template-name>-<input-type>` for inputs and the exact full dataset for streams. A template's absent `data_streams` selects every top-level data stream, an empty list selects none, and a selector resolves only as an exact dataset or `<package-name>.<selector>`. - [ ] **Step 4: Implement package dependency and secret classification**

`SecretSchema` holds:

```rust
struct SecretSchema {
    package_vars: BTreeSet<String>,
    input_vars: BTreeMap<String, BTreeSet<String>>,
    stream_vars: BTreeMap<(String, String), BTreeSet<String>>,
}
```

Parse `item.vars`, `item.policy_templates[*].{name,data_streams,inputs[*].{type,vars,streams[*].{data_stream.dataset,vars}}}`, and modern `item.data_streams[*].{dataset,streams[*].{input,vars}}`. Variable arrays are optional. Each definition needs a non-empty unique `name`; `secret` is optional and defaults false, but a present non-boolean value is `http`. Template names, composite input keys, selectors, full datasets, stream inputs per dataset, and resulting composite stream keys are unique.
