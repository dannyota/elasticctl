# elasticctl 0.2.1 Design

## Outcome

0.2.1 repairs the Windows durability failure found by the 0.2.0 CI run and
finishes the compatibility and contract work deferred from 0.2.0. It does not
add a management surface or change the default scope of any command.

The patch contains five deliverables:

1. File durability works on Windows for pull and change-report transactions.
2. Exception-list, prebuilt-rule, and rule-source operations reject unverified
   stack versions with a typed `unsupported` error before calling the feature
   route.
3. Hosted hostname fallback matching is case-insensitive and ignores a final
   DNS dot.
4. Exception drift and CLI exception contracts have direct regression tests.
5. The `immutable` rule-source partition is proved on the oldest supported
   fixture version. Compatibility below 9.5.1 remains unclaimed.

The 0.2.2 CI and platform-proof queue remains separate. The Windows bug ships
in 0.2.1 because it already prevents the current CI suite from passing.

## Considered approaches

### 1. Cache capabilities in `Transport` and gate API routes — selected

`Transport` owns a `tokio::sync::OnceCell<Capabilities>`. Feature-route code in
`elasticctl-api` asks the transport for the cached probe before its first HTTP
request. This keeps the probe count at one, preserves existing API function
signatures, and protects both CLI and library callers.

### 2. Gate only in CLI command adapters

This is smaller, and the existing CLI `Context` already has a capability
cache. It leaves direct `elasticctl-api` callers receiving the generic server
404 that 0.2.1 is meant to replace. The published API would then make a weaker
contract than the binary.

### 3. Pass `&Capabilities` through every API function

This makes the dependency explicit but changes public signatures throughout
`elasticctl-api`. A patch release must not impose that migration when the
transport can provide the same one-probe contract internally.

## Windows durability repair

Rust's `File::open` creates a read-only handle. On Windows, `sync_all` calls
`FlushFileBuffers`, which requires a handle opened with write access. Pull and
report transactions currently write and close a file, reopen it read-only,
then sync it. Windows returns `Access is denied`; Unix accepts the same call.

Every file-sync implementation in the production filesystem adapter and its
failure-injection test adapters will reopen the existing file with
`OpenOptions::new().write(true)`. Directory syncing remains unchanged: Unix
syncs directories, while Windows treats directory sync as unavailable after
syncing each payload and journal file.

The existing Windows tests are the regression test. They exercise staged pull
files, pull journals, report payloads, report journals, rollback, and recovery.
The failing 0.2.0 run provides the red half of the test cycle; the next Windows
run must provide the green half. The Windows-only unused `Write` import warning
in configuration code is removed by scoping the import to the Unix writer.

## Capability model

`elasticctl-core` gains a public `Feature` enum with these variants:

- `ExceptionLists`
- `PrebuiltRules`
- `RuleSourceScoping`

Each feature has the same verified floor in 0.2.1: Kibana 9.5.1. The floor is
evidence, not a claim about when Elastic first introduced each route. The
repository has complete self-managed and Hosted fixtures at 9.5.1 and a
Serverless fixture at 9.6.0. It has no fixture below 9.5.1.

`Capabilities::require_feature` parses the status version as semantic version
data and returns `ErrorKind::Unsupported` when the version is older than 9.5.1
or cannot be parsed. The error names the feature, deployment flavor, reported
version, and verified floor. Versions at or above the floor proceed. Flavor
classification remains independent of the feature floor.

`Transport::capabilities` caches `GET /api/status`. `Context::capabilities`
delegates to that cache instead of maintaining a second cache. Commands such
as `info`, which already need capabilities, do not issue a second status
request when they call a gated route later through the same transport.

Feature gates sit at the HTTP boundary:

- Exception container and item routes require `ExceptionLists`.
- Public prebuilt status and install routes require `PrebuiltRules`.
- A rule `_find` using `custom`, `prebuilt`, or `customized` source filtering
  requires `RuleSourceScoping`.
- An all-rules query does not require the rule-source feature.
- Selectors and tags that resolve to explicit rule IDs keep their current
  behavior and do not gain an `immutable` dependency.

Local-only work remains local. `exceptions validate` and an import dry run
without `--skip-existing` do not build a transport or probe the stack. An
import that reads existing objects or applies the upload probes immediately
before its first feature request.

## Hosted fallback normalization

The Cloud edge response header remains the primary Hosted signal. The hostname
fallback normalizes only the extracted host: ASCII lowercase followed by
removal of a final DNS dot. Suffix boundary checks remain unchanged, so
`NOTFOUND.IO.` does not match `found.io`, while
`ABC.KB.EXAMPLE.FOUND.IO.` does.

Tests cover uppercase suffixes, a trailing dot, both together, ports, bare
suffixes, lookalike domains, and suffix text in a path or query.

## Exception contract coverage

API integration tests call `state::diff` directly and assert the serialized
contract for:

- a locally added container;
- a modified container with field-level before and after values;
- a remote-only container, which is reported but never deleted;
- an added item;
- a modified item with field-level before and after values;
- a removed item, which is the only actionable exception deletion; and
- a clean rule and exception mirror where `clean` is true.

The tests derive expected changes from literal fixtures. They do not assert on
mock call counts as a substitute for drift behavior.

CLI integration tests add the missing command contracts:

- `exceptions list` forwards type, tag, and namespace filters and renders the
  matching summaries;
- `exceptions validate` succeeds without configuration or network access;
- an import with mixed server outcomes reports successes and failures and exits
  nonzero;
- `--skip-existing` excludes existing containers and items from the upload and
  reports skipped and pending counts; and
- a failed qualified delete keeps `list_id` and `namespace_type` in the error
  report and exits nonzero.

## Oldest-version evidence

The 9.5.1 self-managed fixture set is the compatibility floor. Fixture coverage
must prove that custom and prebuilt `immutable` partitions sum to the complete
scoped corpus. A negative mock omits `immutable` and proves that a
non-exhaustive partition returns typed `unsupported` instead of an empty,
apparently valid result.

If a stack older than 9.5.1 can be provisioned during the patch, it may add a
new fixture set and lower a feature floor only when the same partition proof
passes. Without that recording, documentation and errors continue to state
9.5.1 as the verified floor.

Fixture files are recorded through `cargo xtask record` and never hand-edited.
All three flavor directories keep the same operation names.

## Release and verification

After the contracts pass, the workspace packages move to 0.2.1 and the
changelog records the Windows repair, capability errors, hostname
normalization, and test evidence. No tag, GitHub Release, or crates.io publish
is part of implementation without a separate release request.

Required local gates are:

```bash
cargo fmt --all --check
cargo clippy --locked --workspace --all-targets -- -D warnings
cargo test --locked --workspace
./scripts/check-packages.sh
./scripts/check-fixtures.sh
cargo publish --workspace --dry-run
```

The GitHub Actions Windows job must then pass the state integration tests,
transaction unit tests, and report transaction unit tests that failed or were
skipped in the 0.2.0 run.
