# elasticctl 0.8.0 MCP Task Tools Implementation Plan

**Goal:** Ship four read-only task tools, two `rules_list` threat filters,
static server instructions, and the twelfth conformance contract, with the
decoder measurements recorded first.

**Architecture:** Add `elasticctl_api::compose` for fixed request plans and
typed reports. Add `tools/compose/` adapters in the MCP crate that validate,
call, and project. Reuse the 0.7 target, schema, error, transport, admission,
deadline, cancellation, and output boundaries unchanged.

**Tech Stack:** Rust 2024 / Rust 1.97.1, rmcp 3.9.0, Tokio, serde/schemars,
wiremock, assert_cmd, jsonschema, recorded fixtures, xtask.

**Spec:** [0.8 design](../specs/elasticctl-mcp-tasks-design.md), sections 1
to 7 and 10 to 13; [0.7 MCP design](../specs/elasticctl-mcp-design.md);
[research](v0.8-research.md).

Status: planned on 2026-11-10 at `f7c9fe5`, workspace version 0.7.4, and
revised the same day after independent review. No task has started. Work
starts from the released 0.7.5, which ships `rules_ops::list_page` and
`rules::find_first_by_name` behind `rules_list`. Release and publication need
separate approval.

Owner decisions of 2026-11-10 that this plan follows: the bounded
`rules_list` page is 0.7.5, not 0.8.0; `resources/list` reads nothing from
Elastic; `_resolve/index` and execution messages are on by default with no
new flag; rows ordered by name and fixture directories for 9.7.0 and 9.5.6
that hold only the new operations are accepted; every 0.8 release passes the
three-flavor matrix.

## Global Constraints

- No `clap` type enters the MCP library, API, or core. MCP never depends on the CLI crate.
- Use `rmcp = "=3.9.0"`, `default-features = false`, with `server`, `macros`, and `transport-io`. Add no feature and no dependency.
- Input line: 262,144 bytes; structured content: 262,144 bytes; outbound frame: 1,048,576 bytes; upstream body: 16,777,216 decoded bytes. Four active calls; the fifth returns `busy`. Whole-call timeout 1 to 120 seconds, default 30.
- The default catalog is exactly the 24 names of design section 7, in that order; 26 with `--allow-query-tools`. No existing tool is renamed, removed, or given a new required input.
- Requests inside a call run one at a time in the order of the plan tables in design sections 5 and 6. Caps: 5 exception lists, 5 case details, 5 recent alerts, 16 patterns, 8 packages, 1,000 integration policies in one page, 2,048 message bytes, 500 rules per corpus page, 4,000 rules, 2 passes. Request maxima: 19, 14, 29, and 16.
- A value that becomes a URL path segment is refused when it is exactly `.` or `..` (design section 10.4). Path tests assert the path the mock server received.
- Part failures follow design section 4.1: `auth`, `connection`, and `timeout` fail the call; other kinds make the part `unavailable`.
- Every request uses `ServerState::transport()`. No task tool uses the query transport, an internal Kibana route, PUT, PATCH, or DELETE.
- No tool accepts a target, credential, path, URL, raw query, or index name. Remote text appears only inside `data`.
- CLI output and every existing snapshot stay byte-identical. `rules_ops::list`, `rules_ops::list_page`, and `rules::find_all` keep their behavior.
- Every mock body copies a recorded fixture. Fixtures are recorded, marker-scoped, and never hand-edited.
- Each Rust file stays at or under 700 non-test lines; `scripts/check-lengths.sh` passes with no baseline entry added.
- Local builds use two jobs, tests use four threads, one build-heavy process at a time.
- Keep development versions at the released value; release preparation performs the coordinated bump.
