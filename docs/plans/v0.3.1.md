# elasticctl 0.3.1 Implementation Plan

Patch release in the 0.3 search area. Spec: `elasticctl-design.md` §4.7, §5.3,
§11; `elasticctl-search-design.md` §3, §5, §6. Tasks are Haiku-sized and
test-first.

## Order and dependencies

- Tasks 0 and 1 are live and time-boxed (trial expires 2026-08-26); they touch
  no shared files and may run in parallel.
- Tasks 2 and 3 share `cli.rs` and `cmd/search.rs`, so they run sequentially
  (AGENTS.md: parallel tasks share no files).
- Task 1's verdict sets `--search`'s field scope for Tasks 4 and 5.
- Task 4 builds on Task 1; Task 5 builds on Task 4's filter builder.

## Task 0 — Publish the search conformance matrix

The search contract already exists (`xtask/src/conformance.rs:141`); the report
is missing, and the validation script predates it.

- Update `scripts/check-conformance-reports.sh`: glob both `v0.2.*` and
  `v0.3.*`, expect 6 contracts for `v0.2.*` (the original six) and 7 for
  `v0.3.*` (adds `search`). Today it hardcodes 6 contracts and `length == 6`.
- Run `cargo xtask conformance --flavor serverless|ech|traditional
  --report-dir docs/conformance/v0.3.1` against the live stacks. `--report-dir`
  is required (`conformance.rs:70`).
- Publish `docs/conformance/v0.3.1/{flavor}-{stackversion}.json` (e.g.
  `serverless-9.6.0.json`) plus `findings.md`, matching the v0.2.x layout.
- Gate: no sample indices remain; baseline prebuilt count unchanged.
- Done when the three reports + findings pass
  `./scripts/check-conformance-reports.sh`.

## Task 1 — Probe public `_find` field coverage

Gates `--search`'s field scope. Live investigation, no product code.

- Against a live stack, test whether the public `_find` KQL filter reaches
  `alert.attributes.description` and `alert.attributes.query` (rules), and
  name-substring on `exception-list.attributes.name` (exceptions).
- Measured today: `name`, `type`, `enabled`, `ruleId`, `tags`, `severity`, and
  the source fields (`immutable`, `ruleSource.isCustomized`) map through
  `RuleFilter::to_kql`; `description`/`query` are unmeasured.
- Record the result in design §4.7. If description/query are not reachable,
  `--search` descopes to name substring + tags (already the spec's fallback).

## Task 2 — ES|QL export payload: `columnar` and `format: csv`

Files: `crates/elasticctl-api/src/search/esql.rs`,
`crates/elasticctl-cli/src/cli.rs`, `crates/elasticctl-cli/src/cmd/search.rs`,
`crates/elasticctl-cli/src/main.rs` (and `render.rs` if the raw-CSV path needs
it).

Test first:

- `run_async` sends `columnar: true` in the `/_query/async` body (wiremock
  assert).
- A column-major `values` payload decodes and transposes to row objects (the
  current decoder rejects rows whose `cells.len() != columns.len()`,
  `esql.rs:66`).
- A `format: csv` response (raw text + header row) is written to `--out` without
  being decoded as `EsqlResponse`.

Implementation (measured, search-design §9):

- `columnar: true` returns `values` column-major (one array per column); the
  decoder/renderer must transpose to row objects.
- `format: csv` returns raw CSV text, not `{columns, values}`. It is an
  alternative to `columnar`, never combined with it. The CSV branch streams text
  to `--out` (may reuse the `{"text": …}` convention in `main.rs`); the non-CSV
  branch sends `columnar: true`.
- Only the `--out` export path changes; a peek is unchanged.

## Task 3 — DSL hit metadata: `--with-meta`

Files: `crates/elasticctl-api/src/search/dsl.rs`,
`crates/elasticctl-cli/src/cli.rs`, `crates/elasticctl-cli/src/cmd/search.rs`.

Test first:

- `decode` keeps `_id`, `_index`, `_score` on `DslHit` (dropped today,
  `dsl.rs:30`).
- `search dsl ... --with-meta` renders `_id`/`_index`/`_score`; without the flag
  output is byte-identical to 0.3.0.

Implementation: `DslHit` gains `id`, `index`, `score`. `sort` stays on `DslHit`
(paging needs it, `dsl.rs:126`) but stays out of rendered output and out of
`--with-meta`.

## Task 4 — `--search` on `rules list` and `exceptions list`

Files: `crates/elasticctl-api/src/rules.rs`,
`crates/elasticctl-api/src/exceptions.rs`, `crates/elasticctl-cli/src/cli.rs`,
`crates/elasticctl-cli/src/main.rs`, `crates/elasticctl-cli/src/cmd/rules.rs`,
`crates/elasticctl-cli/src/cmd/exceptions.rs`.

Test first:

- `RuleFilter::to_kql` turns `search` into the right KQL (name-substring, plus
  description/query if Task 1 allows), combined with the structured filters.
- `exceptions list --search <text>` matches by name substring.
- On `rules list`, `--search` and `--filter` conflict (clap `conflicts_with`).

Implementation: `RuleFilter` gains `search: Option<String>` (distinct from
`name` exact and `query` raw KQL); `ListFilter` gains `search` for name
substring. `main.rs` builds the structs from clap args (`main.rs:63`, `:172`),
so the flag must be plumbed there.

## Task 5 — `--search` on `state pull`/`diff`/`push`

Files: `crates/elasticctl-api/src/state/mod.rs` (`Scope`, `scope_of`,
`Scope::remote`, `Scope::describe`), `crates/elasticctl-cli/src/cli.rs`,
`crates/elasticctl-cli/src/main.rs`.

Test first:

- `scope_of` with `--search` resolves to a `rule_ids` scope, so `Scope::remote`
  reads via `find_by_rule_ids`.
- `Scope::describe` names the `--search` selection, so a `push` guard banner
  reports the scoped apply (same contract as `--tag`).

Implementation: `--search` is a new narrowing dimension alongside `--tag` and
selectors. Unlike `--tag` (which reuses `r.tags().contains(&tag)`,
`selection.rs:151`), `--search` needs a new local-side matcher — name-substring
(plus description/query per Task 1) against local rule files. Reuse Task 4's
server-side KQL for the remote read.
