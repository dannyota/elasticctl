# elasticctl 0.7.2 MCP Conformance Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prove the complete MCP surface through independent clients and the
three-flavor release matrix, fixing defects supported by that evidence.

**Architecture:** Retain the 0.7.1 server and tools. Extend the test harness
and existing conformance controller. Provision sample objects outside MCP
through reviewed test code; MCP performs only its registered reads.

**Tech Stack:** Rust/Tokio, rmcp client and raw JSON-RPC harness, wiremock,
assert_cmd, existing live support, xtask, Bash/jq, Podman.

**Spec:** [MCP design](../specs/elasticctl-mcp-design.md), especially sections
6-9; [shared conformance contract](../specs/elasticctl-design.md).

Status: proposed, planning only. Start execution after reviewed 0.7.1 work.
This release adds no planned capability beyond the existing read surface.

## Global Constraints

- The default catalog has twenty tools; startup query opt-in adds exactly two.
- The target protocol is 2026-07-28. Also test legacy 2025-11-25 initialization through the SDK compatibility path.
- Input line: 262,144 bytes; structured content: 262,144 bytes; complete outbound frame: 1,048,576 bytes; upstream body: 16,777,216 decoded bytes.
- Four active calls; the fifth returns `busy` immediately. Whole-call timeout defaults to 30 seconds, range 1-120. Shutdown grace is five seconds.
- The eleventh conformance contract is `mcp_reads_existing_verticals`.
- The MCP process sends no mutation, setup, preview, internal-user, async-query, or PIT request. Harness provisioning is separately owned and reviewed.
- Public conformance JSON keys remain `flavor`, `version`, `contracts`, `contract`, `result`, and `error_class`.
- Keep credentials, target identity, user data, raw results, and raw failures out of public evidence. Never hand-edit recorded fixtures.
- Local builds use two jobs, tests use four threads, and only one build-heavy process runs at a time.
- Keep development versions at the released 0.7.1 value; release preparation performs the coordinated bump.

## Ownership and order

The primary coordinates all reviews and owns shared-file integration, Git,
live runs, evidence, and release actions. Sol performs every review and must
not implement the reviewed slice. Terra writes tests and confirmed fixes in
separate worktrees. Luna may prepare mechanical report-validator changes.
Workers have no live, Git, publishing, or delegation authority. Use a skill
ledger with task dependencies, reports, and review verdicts.

| Task | Owned files | Dependency |
| --- | --- | --- |
| 1 | Review-only report to primary | Integrated 0.7.1 candidate |
| 2 | Files named by confirmed findings; one worker per nonoverlapping fix slice | Task 1 |
| 3 | `crates/elasticctl-mcp/tests/client_conformance.rs` | Reviewed fixes |
| 4 | `crates/elasticctl-cli/tests/live/mcp.rs`, prior smoke module, and `tests/live.rs` registration | Reviewed client tests and 0.7.1 Fleet fixture lease |
| 5 | Controller, validator, public evidence, shared specs | Reviewed live contract |

Read-only review work may run alongside inspection of client setup. Editing
tasks run in order. Task 4's worker owns its test registration as part of the
tested slice. The primary owns controller changes and integrates each slice
after review.

## Task 2: Fix confirmed defects and preserve contracts

The owned paths and failing examples come from Task 1's actual findings.
Do not invent defects or broad refactors to fill this task. If there are no
confirmed findings, record it as not needed and proceed.

- [ ] For each finding, the primary writes a bounded brief with the failing input, promised behavior, exact files, and checks. Update the spec first when the fix changes promised behavior. Assign Terra; the reviewer remains separate.
- [ ] Add a regression that reaches the defect through the production router, process, or transport. Run it red, implement the smallest fix, then run its covering tests. Include exact HTTP-request assertions for any claim that no mutation occurred.

```rust
assert_eq!(unexpected_requests.len(), 0);
assert!(!stdout.contains("private-sentinel"));
assert!(!stderr.contains("private-sentinel"));
```

- [ ] Have Sol review the fix range against the original finding and check for new breakage in that range. The primary inspects the diff and reruns checks before integrating and committing. Resolve all release-blocking findings before client/live evidence.
