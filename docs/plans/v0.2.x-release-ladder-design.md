# elasticctl 0.2.x Release Ladder Design

## Outcome

Use the remaining Elastic Cloud trial window to gather cross-flavor evidence,
ship small patches inside the existing 0.2 capability areas, and then deliver
the complete 0.3 search vertical. Release numbers follow verified outcomes;
they are not a daily cadence and do not justify work by themselves.

The sequence is:

1. 0.2.2 hardens CI and release preflight.
2. 0.2.3 proves the existing 0.2 contracts across Serverless, Hosted, and the
   self-managed 9.5.1 compatibility floor.
3. 0.2.4 is skipped because the conformance run found no release-worthy 0.2
   defect.
4. 0.3.0 is next and adds the complete search capability area. Later minor
   releases begin only after 0.3 is complete and trial time remains.

## Release boundaries

Patch releases remain additive within `rules`, `exceptions`, `prebuilt`,
`state`, configuration, diagnostics, transport, and release tooling. A patch
may add a flag or output field to an existing command, fix a defect, improve a
typed error, or extend tests. It may not add a new command group or management
surface.

Search is a new capability area and therefore starts at 0.3. Alert triage,
cases, dashboards, data views, Fleet, agent policies, full value-list content
management, endpoint exception-list management, and selective prebuilt-rule
management remain outside 0.2.x. Each needs its own later minor design.

## 0.2.2 — CI and release preflight

CI resolves the committed dependency graph with `--locked`. One job uses the
workspace's declared Rust version, while the stable-toolchain job continues to
catch forward incompatibility. Windows runs the full CLI smoke suite, including
raw export and report-file paths, rather than only focused transaction tests.

A preflight job runs `cargo publish --workspace --dry-run` with no crates.io
token and no publication step. GitHub Release remains the default release;
crates.io publication still requires separate approval for the exact version.

## 0.2.3 — cross-flavor live conformance

The guarded live suite runs through one target-neutral entrypoint against:

- Elastic Cloud Serverless;
- Elastic Cloud Hosted;
- the self-managed 9.5.1 compatibility-floor lab.

The same contracts run on every target that supports them: diagnostics,
pull-then-diff stability, exception CRUD and bundle round-trip, stale pointer
repair, source scoping, and rule export/import round-trip. Capability-based
skips must name the unsupported feature and verified floor; a generic failure
or silent skip is not a pass.

Live tests remain serialized. Every created rule, exception list, item, and
index uses the existing live marker and is registered for cleanup before its
first mutation. Each run compares post-test rule partitions with its captured
baseline and refuses success while marked objects remain. Prebuilt rules are
read-only ground truth on Cloud targets. The disposable self-managed lab may
install its platform prebuilt pack before baseline capture; the run never edits
an individual prebuilt rule, and the whole lab is destroyed afterward.

Target URLs, deployment IDs, account data, credentials, locations, and live
object content stay in ignored local configuration. Tracked reports contain
only deployment flavor, stack version, contract name, result, and scrubbed
error classification. Fixtures are re-recorded only when an API exchange or a
supported target version changes, and all fixture flavors keep the same
exchange names.

The completed matrix produced 18 passing rows: all six contracts passed on
Serverless 9.6.0, Elastic Cloud Hosted 9.5.1, and self-managed 9.5.1. Every
post-contract cleanup audit passed, final rule partitions matched their
baselines, and the disposable lab and its volumes were removed. The public
[findings](../conformance/v0.2.3/findings.md) contain no failed or skipped row.

## 0.2.4 — skipped after clean conformance

0.2.4 was conditional on the validated finding list from 0.2.3. That list has
no release-worthy defect, so 0.2.4 is skipped and none of its possible work is
scheduled. Its accepted scope would have been limited to:

- confirmed cross-flavor defects;
- clearer typed errors or diagnostics;
- small flags on existing commands;
- additive output fields backed by live evidence;
- performance or pagination fixes within existing reads;
- fixture, test, and documentation corrections.

Every item would have needed a failing fixture, live reproduction, or
deterministic local regression test before implementation.

## 0.3.0 handoff

0.3.0 owns Elasticsearch search through ES|QL and Query DSL. It keeps the
existing dependency direction: CLI adapters parse arguments, `elasticctl-api`
returns typed search values, and `elasticctl-core` owns authenticated transport.
The 0.2.3 findings are classified and no 0.2.4 patch is justified, so search
design is the next work. The 0.3 design must define query input, timeouts,
result limits, pagination, output schemas, flavor differences, and read-only
safety before implementation begins.

## Release gates

Every release requires its version-specific spec and implementation plan,
focused regression tests, the full locked workspace suite, formatting, Clippy,
package-content checks, fixture leak checks, and a successful GitHub Actions
run. Releases that touch live behavior also require applicable live conformance
on every available target and verified cleanup.

Tag only a clean commit whose version and changelog agree. The GitHub Release
must contain the complete binary asset matrix. Do not publish to crates.io
without separate approval for that exact version.

## Failure handling

A target mismatch changes the evidence, not the expected server. Record the
exchange safely, classify whether the defect is in code, fixture, test, or
spec, and fix the authoritative source. A failed cleanup blocks further live
mutation on that target until the marked objects are removed. Loss of a trial
target reduces the proven matrix; it does not permit a compatibility claim
based on another flavor.
