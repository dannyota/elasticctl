# elasticctl 0.8.2 MCP Client Matrix Implementation Plan

**Goal:** Prove the complete 0.8 surface with two real product clients,
close the remaining protocol test gaps, and fix only defects that this
evidence confirms.

**Architecture:** Keep the 0.8.1 server, tools, resources, prompts, and live
contract. Add one integration test file, one stdio shim script, the client
evidence, and a three-flavor matrix run on the release commit. No capability
is added.

**Tech Stack:** Rust/Tokio, rmcp 3.9.0 client and the raw JSON-RPC harness,
wiremock, jsonschema, Bash, Podman, the local lab, Claude Code and Codex CLI
as product clients.

**Spec:** [0.8 design](../specs/elasticctl-mcp-tasks-design.md), sections 10
to 13; [0.7 MCP design](../specs/elasticctl-mcp-design.md) sections 6 to 8.

Status: planned on 2026-11-10 and revised the same day after independent
review. Starts from the released 0.8.1 tag. Release and publication need
separate approval.

## Global Constraints

- The default catalog has 24 tools; the query flag adds exactly two. Five listed resources, four templates, four prompts. No schema, name, URI, prompt text, or output field changes in this patch unless a confirmed defect requires it and the spec changes first.
- Limits are those of design section 10.1 and 0.7 section 6.
- Model-driven product clients run only against the local lab. Tool results carry `target.host`, and those clients send results to their model providers. Never point them at a trial deployment.
- Client configuration lives in a scratch directory outside the repository. Never create or commit `.mcp.json`, `.vscode/mcp.json`, or user client settings. Remove any entry a client command adds.
- The server has debug off, so no live request log exists. Captured frames come from the stdio shim only. Raw frames, model transcripts, and client logs stay in private files.
- A client behavior is recorded as observed, not sent, or not testable. Documentation and source reading never count as a test.
- The three-flavor matrix is a release gate for 0.8.2, exactly as for 0.8.0 and 0.8.1. It runs on the release commit after every fix is integrated. The plan is to run it inside the current trial window; if the window has closed, the owner supplies replacement Serverless and Hosted stacks and 0.8.2 waits for them. The product clients still run only on the lab.
- Keep credentials, target identity, user data, and raw results out of public evidence. Never hand-edit a fixture.
- Local builds use two jobs, tests use four threads, one build-heavy process at a time.
- Keep development versions at the released 0.8.1 value; release preparation performs the bump.

## Task 1: Close protocol test gaps

**Files:** Create `crates/elasticctl-mcp/tests/task_surface_conformance.rs`.
Helpers stay in this file.

Coverage that exists and must not be duplicated:

| File | Proves |
| --- | --- |
| MCP `tests/client_conformance.rs` | 0.7 tools: output-schema validation, busy, deadline, cancel, input-line cap through the rmcp client |
| MCP `tests/alert_context_tool.rs` and its three siblings | Each task tool: plan order, caps, part failures, schema validation |
| MCP `tests/resource_protocol.rs`, `tests/prompt_protocol.rs` | Lists, reads, errors, admission, prompt texts on both paths |
| MCP `tests/sdk_client_protocol.rs` | rmcp client lists and one call per surface on both paths |
| CLI `tests/mcp.rs` | Both binaries, both protocols, exact catalogs and lists |

- [ ] One wiremock target serves the full fixture set. Through the rmcp client, call all 24 default tools and both query tools once and validate every success and one failure per tool against its declared `outputSchema` with `jsonschema`. This is the single place that covers the whole 26-tool catalog at once.
- [ ] For each of the nine resource shapes, parse the read text and validate it against the output schema of the tool that design sections 8.2 and 8.3 name.
- [ ] Count requests with the recording mock in one table-driven test that uses maximum-work inputs (every referenced list exists, every pattern sends a request, every package is valid, selector by name): `alert_context` 19, `rule_health` 14, `rule_readiness` 29, `detection_coverage` 8 for 4,000 rules and 16 when the first pass fails verification, `rules_list` 1 and 4 for an empty source-only result. A second table uses degraded inputs (a missing list, an exclusion, 1,001 integration policies, a 4,001-rule corpus) and asserts the lower exact counts. No input may exceed a maximum.
- [ ] Mixed admission through the rmcp client against a delayed target: two tool calls and two resource reads held, then a fifth tool call and a fifth read both return `busy`, a `prompts/get` and all four list requests still succeed, and the session works after release.
- [ ] Through the raw harness on both paths: a 262,145-byte line after a successful resource read ends the connection with only the static diagnostic; a resource read whose text is exactly at the structured cap succeeds and one byte above fails.
- [ ] Sentinel sweep: one run places a credential-shaped sentinel in every excluded upstream field used by the four task tools and asserts its absence from stdout and stderr across all 24 tools, nine reads, and four prompts.
- [ ] Run `cargo test --locked -p elasticctl-mcp --test task_surface_conformance --jobs 2 -- --test-threads=4` and record the first result. Behavior that is already correct may pass at once. Route a confirmed failure through Task 3. Obtain review.

## Task 2A: Keep the stdio shim in the tree

**Files:** Create `scripts/mcp-stdio-shim.sh` and
`scripts/test/mcp-stdio-shim-test.sh`.

**Interface:** `mcp-stdio-shim.sh <log-dir> -- <command> [args...]` runs the
command, copies its stdin to `<log-dir>/in.jsonl` and its stdout to
`<log-dir>/out.jsonl`, passes stderr through, forwards EOF and signals, and
exits with the command's status. It creates the directory with mode 0700 and
the files with mode 0600, refuses a log directory inside a Git work tree, and
prints nothing itself.

- [ ] Write the test first: byte-identical pass-through in both directions with a fake line server; exit status preserved; EOF reaches the child; file modes; refusal inside the repository; no output from the shim.
- [ ] Implement with Bash, `tee`, and process substitution only. Run the test and `shellcheck` if installed. Obtain review.

## Task 2B: Run two real product clients on the lab

Primary only. The rmcp client and the raw harness are protocol tests, not
product clients.

- [ ] Client pair: Claude Code and Codex CLI, at the versions installed on the evidence host on the day of the run (2.1.321 and 0.167.0 at planning time). Record exact versions and the OS. An unavailable client is an evidence gap, never a pass.
- [ ] Boot the lab with a job-local Podman socket and run `lab/seed.sh`. Through the CLI, import one marker rule with a `threat` entry and a marker exception list. Create no other object. Lab teardown is the cleanup; verify zero lab containers and volumes afterward.
- [ ] Write the README launch stanza to a scratch file that wraps the built `elasticctl` binary in `scripts/mcp-stdio-shim.sh` with a private log directory and a lab profile.
- [ ] Drive each client non-interactively through this script, one step per client run where the client allows it:
  1. Ask which elasticctl tools exist. Record, from the frames, the negotiated protocol and whether `tools/list` was sent once.
  2. Ask for the health of the marker rule by `rule_id`. Require a `rule_health` call and its result in the frames.
  3. Ask for detection coverage by technique, then for the rules behind the marker technique. Require `detection_coverage` and `rules_list` with `technique`.
  4. Ask to check the marker rule's data readiness. Require `rule_readiness`.
  5. Ask to triage an alert id that does not exist. Require `alert_context` and the normalized not-found failure.
  6. Reference a listed resource: in Claude Code, `@elasticctl:elasticctl://stack/info` in the prompt; in Codex, ask it to list and read elasticctl resources. Record whether `resources/list` and `resources/read` appear.
  7. Ask each client to read `elasticctl://stack/rules/<marker rule_id>`. Record whether a template URI that is not listed is sent.
  8. Invoke a prompt: in Claude Code, `/mcp__elasticctl__review_rule_health <marker rule_id>`; in Codex, whatever prompt entry point the installed version offers, or none. Record whether `prompts/list` and `prompts/get` appear and whether the following tool call matches the prompt text.
  9. Ask for a `rules_list` with `limit: 0`. Record whether the client sends it and receives `invalid_argument`, or rejects it locally.
  10. Exit. Require the child to end with no orphan process.
- [ ] From the frames alone, fill measurement M11: per client and method, observed or not sent, for `server/discover`, `initialize`, `tools/list`, `resources/list`, `resources/templates/list`, `resources/read`, `prompts/list`, `prompts/get`, `completion/complete`, and `subscriptions/listen`.
- [ ] Fill measurement M12 from each client's own transcript or debug output: whether the tool definitions were deferred and whether the server instructions were loaded. If a client exposes neither fact, record not testable.
- [ ] Do not inject synthetic requests through a client, and do not report a server error for a call a client rejected locally. A client-observed server defect goes through Task 3.
- [ ] Use `claude -p --mcp-config <scratch>/mcp.json --strict-mcp-config` with an allowed-tools list naming the elasticctl tools, and `codex exec` with an inline `-c mcp_servers.elasticctl.*` override. If a client needs a persistent entry, add it, remove it after the run, and record that.

## Task 3: Fix defects confirmed by evidence

The owned paths and failing inputs come from a failure that Task 1 or 2B
observed. Do not invent defects or refactors to fill this task. If nothing
fails, record it as not needed.

- [ ] For each finding the primary writes a bounded brief: failing input, promised behavior, exact files, and checks. When the fix changes promised behavior, update the spec first, in the same commit.
- [ ] Add a regression that reaches the defect through the production router, process, or transport. Run it red, make the smallest fix, run its covering tests. Include exact request assertions for any claim that nothing was written.
- [ ] A reviewer checks the fix against the finding and for new breakage in that range. The primary inspects the diff and reruns the checks before integrating.
- [ ] Integrate every fix before Task 4, so the matrix runs on the commit that ships. A runtime fix that lands after Task 4 (in `crates/elasticctl-mcp/src`, the core transport, the CLI MCP dispatch, or an API function a tool calls) requires rerunning both MCP contracts on all three flavors.
- [ ] A client quirk that is not a server defect is recorded in the findings and, where it helps operators, in the README. It does not change the server.

## Task 4: Run the twelve-contract matrix

Primary only, after Tasks 2B and 3.

- [ ] Run the read-only preflight of the 0.8.0 plan Task 7 on both Cloud targets.
- [ ] Run `CARGO_BUILD_JOBS=2 cargo xtask conformance-matrix --report-dir docs/conformance/v0.8.2`. Require three reports with twelve `pass` entries each. A failed contract with clean cleanup is a defect: route it through Task 3 and rerun that flavor with `--flavors <name>`.
- [ ] If a trial target cannot be reached, stop and tell the owner. The owner supplies a replacement stack; seed it with `cargo xtask seed`, confirm its baseline, and run the matrix there. 0.8.2 does not ship on fewer than three flavors, and no earlier report stands in for this one.
- [ ] Verify lab teardown and that Hosted keeps running. Record the source commit, UTC time, measured versions, and negotiated protocol per child for Task 5.
