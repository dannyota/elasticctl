# elasticctl 0.1.3 Implementation Plan

A patch release that closes the last v0.1.x gaps before 0.2 opens a new
capability area. It has two slices: fixture parity across the three flavors,
already landed, and a corpus reader that no longer stops at the result window.

Everything here is additive under 11.1. No command, flag, JSON field, error
kind, or exit code changes meaning. A corpus under 10,000 rules — every real
corpus today — produces byte-identical output to 0.1.2.

## 1. Global constraints

- The spec is already updated for this release. `docs/specs/elasticctl-design.md`
  sections 5.2, 7, and 13 describe the target behaviour. Where this plan and the
  spec disagree, the spec wins and the plan is wrong.
- Command functions return typed values and never print.
- `clap` types stay out of `-api` and `-core`.
- No task asserts an unmeasured API shape. Section 3 lists what was measured
  and when.
- Fixtures are recorded, never hand-written or hand-edited.

## 2. Design decisions made in this plan

### 2.1 `rules export` was never an escape hatch

0.1.2 refuses a corpus above the window with an error pointing at
`rules export`. That advice is wrong and ships today. Export has its own
10,000 cap from `xpack.securitySolution.maxRuleImportExportSize` and answers
`Can't export more than 10000 rules` with a 400.

The generic saved-objects export does not help either. The security rule types
register `isExportable: false`, so detection rules cannot be read through it at
any size. No public API returns more than 10,000 rules in one call.

Fixing the message is not optional and does not depend on the reader landing.

### 2.2 Partition on rule type, not tags

Above the window, read the corpus with one `_find` per rule type. Every rule
has exactly one `params.type`, so the slices are disjoint and exhaustive. In
the measurement against 2,066 rules, the seven types sum to the corpus.

Tags were the obvious alternative, but they are unsound. A rule may carry
several tags or none, so tag slices double-count some rules and drop others.
There is no sum that could detect this.

A type larger than the window splits again on `alert.attributes.enabled`
(measured 2 / 2,064). Fourteen slices put the ceiling near 140,000.

### 2.3 Exhaustiveness is checked, never assumed

The slice totals must sum to the corpus `total`, or refuse the read as a short
read. This is the rule 0.1.2 already applies to a server returning fewer rules
than it counted. Without the check, a rule type added by a future stack version
would silently vanish from every `pull` and appear as remote-only in every
`diff`.

### 2.4 The fast path does not move

One request remains the behaviour for any corpus under the window. Partitioning
is a fallback reached only when `total` exceeds it. Paying seven requests for a
2,066-rule read would forfeit the result of 0.1.2's 5.2 work.

### 2.5 The internal cursor route is rejected

`POST /internal/detection_engine/rules/_search` exposes `search_after` and
would remove the ceiling outright. It is `access: 'internal'` and unversioned.
This tool spans three deployment flavors, so its primary read path cannot rely
on a route none of them promise to keep.

### 2.6 What this release deliberately does not do

- **Remove the ceiling.** 140,000 is a bound, not infinity. A slice still over
  the window after both partitions refuses and names the limit.
- **Partition by default.** See 2.4.
- **Raise `maxRuleImportExportSize`.** It is settable in `kibana.yml` on
  self-managed and fixed on Serverless. Telling an operator to reconfigure
  Kibana is not a CLI behaviour.

## 3. Measured facts this plan relies on

Measured 2026-08-13 against Serverless 9.6.0 (2,066 rules) unless noted.

| # | Fact | Recorded in |
|---|---|---|
| 1 | The 7 `params.type` values sum to exactly 2,066 | spec 5.2 table |
| 2 | `enabled` splits 2 / 2,064, summing to the corpus | spec 5.2 |
| 3 | `params.ruleId` filtering returns 1 for a live id, 0 for an absent one | spec 7 |
| 4 | `params.type` and `alertTypeId` agree exactly (455 `query` rules each) | spec 7 |
| 5 | `_export` caps at 10,000 (`maxRuleImportExportSize`), 400 on exceed | spec 7 |
| 6 | `maxRuleImportPayloadBytes` is read by the import route only | spec 7 |
| 7 | Security rule types register `isExportable: false` | spec 7 |
| 8 | Public `_find` has no `search_after`; only the internal route does | spec 7 |

Facts 5-8 come from the Kibana source on `main` and official docs, not from a
probe. Triggering them needs a corpus larger than any stack available here.
They are cited in the spec, not inferred.

## 5. Tasks

### Task 1: Fixture parity — complete

All three sets hold 14 fixtures and record response headers.
`traditional-9.5.1` is measured to lack `x-found-handling-cluster`, closing the
negative half of the Hosted signal, and its `rules_preview_hits` fixture
confirms `rules preview` on self-managed.

### Task 2: Partitioned corpus reads

Replace the refusal above the window with a partitioned read, per spec 5.2.
Correct the refusal message so it no longer points at `rules export`.

Acceptance:

- A corpus under the window is one request, and `rules list` output is
  byte-identical to 0.1.2.
- A corpus above the window is read as one `_find` per rule type and returns
  every rule.
- A rule type above the window is split again on `enabled`.
- Slice totals not summing to the corpus `total` is refused as a short read.
- A slice above the window after both partitions is refused naming the limit.
- No error message mentions `rules export` as a way past the window.
- The fixture test proves the request shape; no test asserts an unmeasured one.

### Task 3: Release

Bump the version, update the changelog, and tag the release. The build matrix
is proven — 0.1.2 shipped a complete 7-target asset list — so no `-rc` tag.

## 6. Review checkpoints

- Task 2 gets Opus review. It feeds `state diff` and `state push`, so a wrong
  corpus read reports fake drift and mis-plans a mutation.
- Before Task 3: full suite green, the live suite green,
  `cargo fmt --all --check`, and
  `cargo clippy --workspace --all-targets -- -D warnings`.
- The `lab/` stack can be torn down once Task 2's fixtures are recorded; it is
  not needed for the partitioned-read tests, which are fixture-driven.
