# elasticctl 0.9.1 MCP Mutation Classes Implementation Plan

Steps use checkbox (`- [ ]`) syntax. Mark a step done only with its evidence.

**Goal:** Add the classes `alerts-triage`, `cases`, and `rules-create`: six
planner tools on the 0.9.0 mechanism.

**Architecture:** Each planner validates input, calls the `-api` planner that
0.9.0 landed, and stores a plan. `plan_apply`, the plan store, the consent
text rules, both confirmation paths, and the audit lines are unchanged, apart
from the two consent rules the owner approved (D39, D40). The only `-api`
change is the `doctor` org-key message (Task 8); no `-core` or CLI source
changes.

**Tech Stack:** As 0.9.0. No dependency change.

**Spec:** [MCP mutation design](../specs/elasticctl-mcp-mutation-design.md),
sections 3 to 8. [Research](v0.9-research.md).

Status: planned. Starts after 0.9.0 is released.

## Global Constraints

- Every 0.9.0 constraint stays in force, including one request per write on
  the no-pool mutation transport and the single-owner rule for shared files.
- The consent text names every object it writes to by identity, shows every
  value it writes in full, and is measured against 8,192 bytes after
  rendering. Nothing is summarized.
- A case status plan exists only when every case has a strictly decoded
  `syncAlerts == false`. The refusal is `case_sync_alerts`, at planning and
  at both checks. A case is created with `syncAlerts: false`.
- No kind is described as exactly reversible in a tool description, a
  result, or a document. A tags plan does not record prior membership.
- This version changes no consent rule, store rule, limit, error code, or
  `-api` function, except three owner-approved changes made spec first in
  Task 0: the single-line action line and the `rule_id`-first create layout
  (D39), the rule create note (D40), and the `doctor` org-key message (shared
  design 7.2, Task 8). Any other need goes to the owner first.
- Checked counter arithmetic is owner-approved, in the `-api` report decoders
  and in the per-kind outcome mapping (design 8.4). A report whose counters
  overflow or exceed the planned count is `unknown` for every kind, including
  `rules_set_enabled`, which 0.9.0 recorded as `applied`.
- Valid classes become `rules-toggle`, `alerts-triage`, `cases`,
  `rules-create`. There is still no `all`.
- With no class enabled the server equals 0.8.2. With only `rules-toggle`
  enabled it equals 0.9.0, byte for byte, in catalog, schemas, and results,
  apart from the out-of-range report above.
- Each new apply is one write: `signals/status`, `signals/tags`,
  `POST /api/cases`, `POST /api/cases/<id>/comments`, `PATCH /api/cases`, or
  `POST /api/detection_engine/rules`.
- MCP never resolves a username and never sends a request to an internal
  Kibana route. `cases_create_plan` passes no assignees.
- A rule created through MCP is disabled. No path in this version enables it
  except a separate `rules_set_enabled_plan` and its own confirmation.
- Keep development versions at the released 0.9.0 value.

## Task 1: Register three classes and six kinds

**Files:** as in the table. This task writes every edit to shared files so
that Tasks 2 to 4 only fill their own modules.

**Interfaces:**

- `MutationClass` gains `AlertsTriage` (`alerts-triage`), `Cases` (`cases`),
  and `RulesCreate` (`rules-create`).
- `ToolId` gains `AlertsSetStatusPlan`, `AlertsSetTagsPlan`,
  `CasesCommentPlan`, `CasesCreatePlan`, `CasesSetStatusPlan`, and
  `RulesCreatePlan`, each gated by its class, with the names of
  [design section 3](../specs/elasticctl-mcp-mutation-design/03-startup-opt-in-and-catalog.md#catalog).
- `plan/kind.rs` gains six `PlanKind` and `Operation` variants holding
  `StatusPlan`, `TagsPlan`, `CreatePlan`, `CommentPlan`, the case
  `StatusPlan`, and `RuleCreatePlan`; for each, the `operation` JSON of
  [design section 5.1](../specs/elasticctl-mcp-mutation-design/05-plans.md#51-content-and-hash),
  the `observe` call, the `apply` call, the outcome mapping of
  [section 8.4](../specs/elasticctl-mcp-mutation-design/08-apply-errors-and-cancellation.md#84-results-and-audit-trail),
  the extra consent lines of
  [section 6.1](../specs/elasticctl-mcp-mutation-design/06-confirmation-protocol.md#61-consent-text)
  (`reason:` for an alert close; `description:` and the static
  `syncAlerts: false` for a new case; `case_id: <id>` as the first detail
  line of a comment plan; the static attached-alerts line for a case status
  plan), `"sync_alerts": false` in the `cases_create` operation, the
  `case_sync_alerts` error code and its static message naming `syncAlerts`,
  the rule that a `cases_set_status` plan and each of its checks require
  `sync_alerts` exactly `false` for every case, the
  credential note for `rules_create`, the rule that a `conflict` error with
  status 409 moves `cases_set_status` and `rules_create` from `applying` to
  `stale`, and
  `cli_equivalent`:

| Kind | `cli_equivalent` |
| --- | --- |
| `alerts_set_status` | `alerts ack`, `alerts open`, or `alerts close`, then the ids, then `--reason <reason>` when set |
| `alerts_set_tags` | `alerts tag`, the ids, then `--add <tag>` and `--remove <tag>` per tag |
| `cases_create` | `cases create --title <title>`, then `--description`, `--tag` per tag, and `--severity` when set |
| `cases_comment` | `cases comment <id> --message <message>` |
| `cases_set_status` | `cases close` or `cases open`, then the ids |
| `rules_create` | `null` |

- The six planners join the mutation tools that the protocol-shape check of
  D36 covers (`tools/context.rs`), so in a mixed session they are
  `invalid_request` before any read, like the 0.9.0 tools.
- `consent.rs` renders the action line on one line (rule 7, D39): a line
  feed in the action shows as U+FFFD. `kind.rs` puts the `rule_id` detail
  line first for `rules_create` and carries the create note of D40, not the
  toggle note.
- `tools/mutations/alerts.rs`, `cases.rs`, and `rules_create.rs` are created
  here with their argument types, input and output schemas, static
  descriptions, and definitions. Each planner body returns `unsupported`
  until its task replaces it.

- [ ] Red tests in `mutation_startup.rs`: each class alone adds exactly its tools plus the four plan tools; all four classes give the 35 and 37 name catalogs in lexical order; `rules-toggle` alone equals the 0.9.0 catalog snapshot; an empty set equals the 0.8.2 snapshot; a tool of a disabled class is the unknown-tool error with zero requests, for all six.
- [ ] Red unit tests in `kind.rs` for each new kind: the `operation` JSON; the outcome mapping from a constructed `-api` report, including `requested > total`; the `cli_equivalent` list; the extra consent lines, with `case_id:` first for a comment; the create note of D40, exactly, for `rules_create`, the toggle note unchanged for `rules_set_enabled`, and no note for the alert and case kinds; the `rule_id` line first for `rules_create`; an action holding a line feed renders as one line with U+FFFD; the classifier input `(kind conflict, Some(409))` gives `stale` for the two kinds and `failed` for the others, and `(kind conflict, None)` gives `unknown` for all.
- [ ] Red CLI process tests: each new class name is accepted alone and in a list; the warning line lists the classes sorted.
- [ ] Red mixed-session test: in a session started with `initialize`, each of the six planners called with another protocol version in `_meta` is `invalid_request` with zero requests and no audit line.
- [ ] Assert annotations for the six planners (`readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true`, `openWorldHint: true`, no `_meta`).
- [ ] Run `cargo test --locked -p elasticctl-mcp --lib --test mutation_startup --jobs 2 -- --test-threads=4` and `cargo test --locked -p elasticctl --test mcp_mutations --jobs 2 -- --test-threads=4` red, implement, green. Obtain review before Tasks 2 to 4 start.

## Task 2: Alert planners

**Files:** `crates/elasticctl-mcp/src/tools/mutations/alerts.rs`,
`tests/mutation_alerts.rs`.

Planner order for both tools: validate input; read the credential identity;
call `alerts_ops::plan_status_by_ids_observed` or
`alerts_ops::plan_tags_observed`; build and store the plan.

- [ ] Red input tests with zero requests: 0 and 21 ids, a duplicate id, an oversized id, an unknown status, `reason` with a status other than `closed`, a `reason` outside the enum, empty `add` and `remove`, 11 tags, a 257 byte tag, a tag in both lists, an unknown key.
- [ ] Red flow tests through the router with `signals_search.json`, `signals_status_ids.json`, `signals_tags.json`, and `authenticate.json` from all three fixture sets, on both protocol paths: plan, confirm, one `POST .../signals/status` or `.../signals/tags`, outcome with `updated` and `unchanged` from the recorded counters.
- [ ] Red consent tests: each alert is named by `_id` on its own detail line; the tags text shows the named adds and removes and nothing that claims to restore earlier tags; a tag with a replaced character is `invalid_argument`.
- [ ] Red drift tests: a status changed in the mock before the question gives `plan_stale` for the status kind; an alert that no longer resolves gives `plan_stale` for both kinds; a changed status does not stale a tags plan.
- [ ] Route proof: the planner sends the identity GET and one `POST .../signals/search` whose body equals the body `resolve_ids` sends; no request reaches `/_security/profile/_suggest` or any `/internal/` path; the status body never carries `query` or `conflicts`.
- [ ] Sentinel test: a rule name with credential-shaped and instruction-shaped text stays on indented consent lines and out of errors and audit lines.
- [ ] Run `cargo test --locked -p elasticctl-mcp --test mutation_alerts --jobs 2 -- --test-threads=4` red, implement, green.

## Task 3: Case planners

**Files:** `crates/elasticctl-mcp/src/tools/mutations/cases.rs`,
`tests/mutation_cases.rs`.

`cases_create_plan` calls `cases_ops::plan_create(t, title, description, tags, severity, &[])`
and stores an empty precondition list. `cases_set_status_plan` refuses with
`case_sync_alerts` before storing anything when any observed case has
`sync_alerts` other than `false`. `cases_comment_plan` calls
`plan_comment_observed`. `cases_set_status_plan` calls `plan_status_observed`
with `CaseStatus::Open` or `CaseStatus::Closed`.

- [ ] Red input tests with zero requests: a title holding a line feed (D39); title of 161 bytes and whitespace only; description of 4,097 bytes; 11 tags; an unknown severity; an `assignees` key (unknown key); message of 4,097 bytes; 0 and 21 ids; status `in-progress`.
- [ ] Red flow tests with `case_get.json`, `case_create.json`, `case_comment.json`, `case_update_status.json`, `case_conflict.json`, and `authenticate.json` from all three sets, on both protocol paths. Create: one POST with `assignees: []`, outcome `created.case_id` from the recorded response. Comment: one POST. Status: one PATCH carrying the planned `version`.
- [ ] Red alert-sync refusal tests through the router: a case with `settings.syncAlerts: true` and `totalAlerts: 2`; a case without `settings`; a case with `"syncAlerts": "false"`; and a list of three cases where only the last has it on. Each gives `case_sync_alerts` with a message naming `syncAlerts`, no plan, no audit `plan_created`, and no PATCH. Both `closed` and `open` targets are refused.
- [ ] Red check tests: `syncAlerts` turned on in the mock after planning gives `case_sync_alerts` and state `stale` at the first check with no question asked; turned on between question and answer gives the same at the second check with no PATCH.
- [ ] Red create tests: the POST body has `settings.syncAlerts` equal to JSON `false`; the consent text has the line `syncAlerts: false`; `operation.sync_alerts` is `false`; `syncAlerts` or `settings` in the tool input is an unknown key.
- [ ] Red consent tests: the create text shows the title on the change line and the full description on continuation lines; the comment text shows `case_id: <id>` as its first detail line and then the full message; two cases with the same title give comment texts that differ by that line; a case title read from the stack with line feeds keeps the comment action on line 1, with U+FFFD, and `case_id:` on line 3; a status plan names each case by id.
- [ ] Red exact-display tests with zero requests: a title, description, message, or tag holding a tab, DEL, a C1 control, U+2028, or a bidirectional control is `invalid_argument`. A case title read from the stack with such a character is shown with U+FFFD and cannot produce a left-margin line.
- [ ] Red drift and conflict tests: a changed title or status stales a comment plan before the question; another comment (a changed `version` only) does not; a changed `version` stales a status plan; the recorded `case_conflict.json` served at 409 on the PATCH after acceptance, through the real `cases_ops::apply_status`, gives `plan_stale`, state `stale` reached from `applying`, and an `apply_finished` audit line with `http_status` 409. The same body served at 500 gives `unknown`.
- [ ] Red replay test for create: after a timeout on the POST the plan is `unknown`, a second `plan_apply` returns `replayed: true`, and the mock saw exactly one POST.
- [ ] Route proof: no DELETE, no attach comment body (`type: "alert"`), no profile lookup.
- [ ] Run `cargo test --locked -p elasticctl-mcp --test mutation_cases --jobs 2 -- --test-threads=4` red, implement, green.

## Task 4: Rule create planner

**Files:** `crates/elasticctl-mcp/src/tools/mutations/rules_create.rs`,
`tests/mutation_rules_create.rs`.

The adapter checks size, shape, exact display, and blank values before I/O so
the caller gets `invalid_argument`. `rules_ops::plan_create` repeats only the
structural refusals of design section 7 (required fields, `enabled`, volatile
fields, dependencies) as a backstop; the adapter is its only caller in this
version.

- [ ] Red input tests with zero requests: a non-object `rule`; 65,537 serialized bytes; missing or non-string `rule_id`, `name`, or `type`; `enabled: true`; each key of `VOLATILE_FIELDS`; non-empty `exceptions_list`, `actions`, and `response_actions`; a string anywhere in the rule holding DEL, a C1 control, U+2028, U+2029, or a bidirectional control.
- [ ] Red flow tests with `rules_create.json` and `authenticate.json` from all three sets, on both protocol paths: the plan for an absent `rule_id` (404 built in the test file); the consent text has one line per field of the stored rule with its whole value, for a rule that carries `threat_query`, `threat_mapping`, `filters`, `threshold`, and a key this version does not know; a multi-line query with tabs is accepted and shown on one line with `\n` and `\t`; the `rule_id` line is the first detail line (D39); the text carries the create note of D40 exactly; after acceptance one `POST /api/detection_engine/rules` whose body has `enabled: false`; outcome `created.rule_id`.
- [ ] Red size tests: the cap is applied to the finished consent text. A rule whose text is exactly 8,192 bytes is planned; one byte more in any field, including a field other than `query`, is `plan_too_large` with nothing stored and no write. There is no separate query limit.
- [ ] Red tests: an existing `rule_id` at plan time is `elastic_conflict` with no plan; a rule that appears between plan and apply is `plan_stale` at the check; a 409 on the POST, through the real `rules_ops::apply_create`, is `plan_stale` with state `stale` reached from `applying`; a 400 on the POST is `failed` with `elastic_http` and status 400.
- [ ] Red test that created rules stay disabled: a request with `enabled` absent stores and sends `false`; a response with `enabled: true` is `unknown` through the `-api` decode failure, never `applied`.
- [ ] Route proof: no PUT, PATCH, DELETE, import, preview, or bulk action.
- [ ] Run `cargo test --locked -p elasticctl-mcp --test mutation_rules_create --jobs 2 -- --test-threads=4` red, implement, green.
