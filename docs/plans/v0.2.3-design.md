# elasticctl 0.2.3 Cross-Flavor Conformance Design

## Outcome

0.2.3 adds repeatable evidence for the existing 0.2 behavior across Elastic
Cloud Serverless, Elastic Cloud Hosted, and the self-managed 9.5.1
compatibility floor. It does not change product behavior. Confirmed product
defects become candidates for 0.2.4 unless they prevent safe cleanup or make a
conformance result invalid.

The release is complete when one target-neutral runner has exercised the same
six contracts on all three targets, verified cleanup, and written public-safe
reports for each target.

## Boundaries

0.2.3 may change the live test harness, `xtask`, test documentation, release
metadata, and conformance reports. It may not change CLI commands, API
orchestration, transport behavior, output contracts, or recorded fixtures.

The runner never provisions Cloud resources. The existing trial Serverless and
Hosted targets are supplied through ignored local environment variables. The
self-managed lab remains disposable: start 9.5.1, install its prebuilt pack,
run conformance, and destroy the lab and its volumes afterward.

Raw target URLs, account or deployment data, credentials, locations, live
object content, and unsanitized failures remain local. The ephemeral lab API
key is held only in the process environment and is not added to `.env`.

## Approaches considered

The selected approach is a typed `cargo xtask conformance` runner. It can probe
the target through the same core transport, invoke each contract separately,
classify results without copying private output into a report, and test its
report and cleanup logic locally.

A shell-only runner would be smaller, but would make deterministic JSON,
failure classification, and output scrubbing harder to test. A GitHub Actions
matrix would put short-lived credentials into repository infrastructure and
would not share the local self-managed lab lifecycle, so it is outside this
release.

## Runner interface

The entrypoint is:

```text
cargo xtask conformance --flavor <serverless|ech|traditional> \
  --report-dir docs/conformance/v0.2.3
```

It reads only the target-neutral variables already used by the recorder and
live suite:

- `ELASTICCTL_KIBANA_URL`
- `ELASTICCTL_ES_URL`
- `ELASTICCTL_API_KEY`
- `ELASTICCTL_SPACE`, defaulting to `default`

The caller maps the ignored `ELASTICCTL_ECH_*` values to those generic names
for Hosted. The lab invocation supplies its generated API key directly in the
environment. The runner does not parse `.env`, accept credentials as command
arguments, or print target configuration.

The explicit flavor is the deployment label used by fixtures and reports. The
runner probes the target before any mutation and refuses a label that does not
match the measured deployment: `serverless` must probe as Serverless, `ech` as
Elastic Cloud Hosted, and `traditional` as self-managed. The probe also
provides the stack version for the report filename.

## Contract execution

The runner owns an ordered table mapping public contract names to the existing
ignored test names:

| Contract | Live test |
| --- | --- |
| `diagnostics` | `doctor_reports_no_failed_checks` |
| `pull_diff` | `a_pull_followed_by_a_diff_is_clean` |
| `exception_round_trip` | `exception_crud_and_bundle_round_trip_preserve_a_marked_list` |
| `stale_pointer_repair` | `a_stale_exception_pointer_is_observed_repaired_and_rewritten_on_import` |
| `source_scoping` | `source_defaults_keep_custom_rules_and_allow_selected_prebuilt_rules` |
| `rule_round_trip` | `a_rule_survives_a_create_export_import_round_trip` |

Each contract runs as an exact test selection with the committed lockfile and
one test thread. The runner waits for it before starting the next contract and
continues after an ordinary contract failure so the report contains the whole
target result. The existing live mutex remains a second guard against an
accidental concurrent invocation inside the test binary.

Test failures carry one machine-readable class marker from the harness:
`contract`, `cleanup`, or `harness`. The runner records only that class. Full
stdout and stderr go under `target/conformance-private/`, which is already
ignored and is never copied to a tracked path. A missing or malformed marker is
`harness`.

The capability floor remains 9.5.1. When a contract prerequisite is not
verified, the runner does not silently pass it. It records `skip` with an
`unsupported` classification that names the feature and the verified 9.5.1
floor. The three release targets are expected to run all six contracts; a skip
is evidence that the intended matrix was not met and must be explained before
release.

## Baseline and cleanup

Before the first contract, the runner captures custom, prebuilt, and customized
rule counts and refuses to start if any rule, exception list, or index carrying
the live marker already exists. Each live test continues to register every
identity before its first mutation and to run its current cleanup guard.

After every contract, the runner checks for marked objects before proceeding.
After the final contract, it also compares all three rule partitions with the
captured target baseline. A cleanup or baseline mismatch makes the target run
invalid, stops further mutation on that target, and exits nonzero. Ordinary
contract failures remain valid evidence when cleanup succeeds.

The self-managed sequence is stricter: start the 9.5.1 lab, seed the complete
prebuilt pack, capture the baseline, run the same runner, and execute
`lab/down.sh` even when the conformance command fails. The release operator
verifies that no elasticctl lab containers or volumes remain.

## Public report

Each valid target run writes one deterministic JSON document named
`<flavor>-<version>.json` in the requested report directory:

```json
{
  "flavor": "serverless",
  "version": "9.6.0",
  "contracts": [
    {
      "contract": "diagnostics",
      "result": "pass",
      "error_class": null
    }
  ]
}
```

The allowed keys are exactly `flavor`, `version`, `contracts`, `contract`,
`result`, and `error_class`. Results are `pass`, `fail`, or `skip`.
`error_class` is null for a pass and otherwise contains only the stable class,
with the feature and verified floor added for an unsupported skip. Reports
contain no timestamp, counts, messages, object identifiers, hostnames, or raw
command output.

The runner writes a report only after the final cleanup audit succeeds. It
exits zero when the target run is complete and safe, even if one or more
contracts recorded `fail`; those findings are the input to 0.2.4. It exits
nonzero for invalid configuration, flavor mismatch, an incomplete test
process, unsafe cleanup, baseline drift, or a report-write failure.

## Testing

Runner unit tests cover argument parsing, flavor/probe matching, deterministic
report serialization, the exact six-contract table, machine-readable failure
classification, and refusal to publish a report after cleanup drift. The live
test harness has local tests proving that registration precedes mutation and
that each conclusion path emits the correct class without exposing its detail
to the report.

The release gate includes formatting, locked Clippy, the locked workspace
suite, package-content checks, fixture-leak checks, and the non-publishing
workspace publish dry run. All three conformance runs must complete safely,
and a leak scan of their tracked reports must pass before tagging 0.2.3. CI and
release preflight must pass on the exact tagged commit. GitHub Release remains
the end of the release; crates.io publication still requires separate approval
naming 0.2.3.

## Findings and follow-up

The 0.2.3 changelog states which targets and versions completed the run and
links to the scrubbed reports. A tracked findings section lists only contract,
flavor, classification, and the decision to defer or block. It never copies a
private log.

If every contract passes, skip 0.2.4 and begin the 0.3 search design. If valid
reports contain failures, 0.2.4 is limited to those evidence-backed fixes and
small existing-surface improvements. A cleanup failure blocks the affected
target and the 0.2.3 release until the marked objects are removed and a clean
run replaces the invalid evidence.
