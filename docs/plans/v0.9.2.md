# elasticctl 0.9.2 MCP Mutation Conformance Implementation Plan

Steps use checkbox (`- [ ]`) syntax. Mark a step done only with its evidence.

**Goal:** Prove the consent flow in two product clients, register the
mutation contract in the release matrix, and fix defects that evidence
confirms.

**Architecture:** Keep the 0.9.1 server. Register the existing live test as
the thirteenth conformance contract, extend the controller and validator, and
close the offline protocol gaps. No capability is added.

**Tech Stack:** Rust and Tokio, the `rmcp` 3.9.0 client and the raw JSON-RPC
harness, wiremock, xtask, Bash and jq, the CI lab (`live-lab.yml`), the
Hosted test deployment, Claude Code and Codex CLI as product clients, a
terminal multiplexer for interactive sessions.

**Spec:** [MCP mutation design](../specs/elasticctl-mcp-mutation-design.md),
sections 2 and 9; [shared conformance contract](../specs/elasticctl-design/08-testing.md#83-cross-flavor-live-conformance).

Status: planned. Starts after 0.9.1 is released, except Task 1, which may run
on the 0.9.1 release candidate. A failure it finds before 0.9.1 ships is a
0.9.1 defect, fixed there rather than in Task 3.

## Global Constraints

- No tool, schema, limit, error code, or consent rule changes in a patch. A
  fix that needs one is a spec change and goes to the owner first.
- The thirteenth contract is `mcp_mutations_plan_and_confirm`. Its ignored
  test has the same name because the controller invokes tests by exact name.
  The twelve earlier contracts keep their names and order.
- Public conformance JSON keys stay `flavor`, `version`, `contracts`,
  `contract`, `result`, and `error_class`. A skipped or unavailable target is
  never a pass, and no substitute report is written.
- No local lab starts (mutation design D35). The self-managed leg runs in
  `live-lab.yml` on a fresh CI lab.
- Model-driven clients run only against the Hosted test deployment
  ([design 9.3](../specs/elasticctl-mcp-mutation-design/09-testing-and-evidence.md#93-real-clients)). Client configuration lives
  in a scratch directory outside the repository. No `.mcp.json`, client
  setting, or hook file is created in the repository or left in the user's
  settings after a run.
- A confirming run is interactive. A non-interactive run can only prove
  refusal.
- The matrix row "Hook answers the form" documents a limit of every server.
  Its result is recorded whatever it is and does not gate the release.
- Raw client logs, pane captures, and child output are private. Public
  findings hold versions, protocol paths, and outcomes only.
- Keep development versions at the released 0.9.1 value.

## Task 1: Close offline protocol and consent gaps

**Files:** create `crates/elasticctl-mcp/tests/mutation_conformance.rs`. New
helpers stay in this file. Do not repeat what the 0.9.0 and 0.9.1 test
targets already prove; read them first and list the gap each new test
closes in its doc comment.

- [ ] Through the `rmcp` client's high-level `call_tool` on the current path, with a handler that accepts with `apply: true`: one call drives both rounds and applies once. With a handler that returns the SDK default (`decline`): `plan_declined`.
- [ ] A handler that accepts with empty content, with `apply: "true"` (a string), and with `apply: 1`: each is `not_confirmed` and nothing is written. This is the blind-accept case.
- [ ] Cross-path: a plan made on a current-protocol session and a plan made on a legacy session have equal hashes for the same change and the same mocked state.
- [ ] Concurrency: eight planners and four `plan_apply` calls at once against a delayed mock. The fifth active call is `busy`; no plan applies twice; the store ends with at most eight open plans.
- [ ] Two `plan_apply` calls for one plan, both carrying a valid round 2 answer for handles issued in sequence: exactly one write.
- [ ] Output schema validation with `jsonschema` for one success and one error result of all eleven mutation tools, and for the `input_required` result against the 2026-07-28 schema fields `resultType`, `inputRequests`, and `requestState`.
- [ ] A 262,145 byte `plan_apply` line ends the connection as in 0.7 and leaves every plan unapplied.
- [ ] Audit completeness: for each of accept, decline, dismiss, stale, expired, discarded, failed, and unknown, the sink received the event sequence of design section 8.4 and nothing else.
- [ ] Run `cargo test --locked -p elasticctl-mcp --test mutation_conformance --jobs 2 -- --test-threads=4`. Behavior that is already correct may pass at once. A confirmed failure goes to Task 3.

## Task 2A: Make the live test the thirteenth contract

**Files:** `crates/elasticctl-cli/tests/live.rs`,
`crates/elasticctl-cli/tests/live/mcp_mutations.rs`.

The test already has the contract's name and steps. This task makes it fit
the controller.

- [ ] Give the root test a doc comment stating that the conformance controller invokes this exact name.
- [ ] Emit the `elasticctl-conformance-class:contract` and `elasticctl-conformance-class:cleanup` lines on the same conditions as the existing MCP read contract, so the controller classifies failures.
- [ ] Honor the controller's confirmed-setup variables the same way `mcp_reads_existing_verticals` does; the contract needs no Fleet setup and must not send one.
- [ ] Offline tests for the classification lines with the fake child harness. `cargo test --locked -p elasticctl --test live --jobs 2 -- --test-threads=4`.
- [ ] Obtain an adversarial review confirming that provisioning order, cleanup, and the set of ids the harness can send are unchanged from the reviewed 0.9.1 harness.

## Task 3: Fix defects confirmed by evidence

The paths and the failing input come from a failure that Task 1, 4, or 5
observed. Do not invent defects or refactor. If nothing fails, record the
task as not needed.

- [ ] For each finding, the integrator writes a bounded brief: the failing input, the promised behavior with its spec section, the exact files, and the checks. Update the spec first when promised behavior changes.
- [ ] Add a regression that reaches the defect through the router, the process, or the transport. Run it red, make the smallest fix, run its covering tests. Include exact request assertions for any claim that nothing was written.
- [ ] Obtain a review of the fix range against the finding, including new breakage in that range.
- [ ] A runtime fix integrated after Task 4 (anything under `crates/elasticctl-mcp/src`, core transport, CLI MCP dispatch, or an `-api` function a mutation tool calls) reruns `mcp_mutations_plan_and_confirm` on every flavor. A fix to the consent path also reruns Task 5. A fix limited to tests, documents, scripts, or `xtask` needs no live rerun.

## Task 4: Run the thirteen-contract matrix

Integrator only. Writes
`docs/conformance/v0.9.2/{serverless,ech,traditional}-<version>.json` and
private logs under `target/conformance-private/`.

- [ ] Source `.env` in the shell that runs the commands. Unset `ELASTICCTL_INGEST_URL`.
- [ ] Read-only preflight: both Cloud targets answer `elkctl info`; each has a nonzero prebuilt count and zero marker objects apart from closed marker alerts, the accepted triage residue of design 9.2.
- [ ] Run the two Cloud legs in one matrix process:

```bash
CARGO_BUILD_JOBS=2 cargo xtask conformance-matrix \
  --flavors serverless,ech --report-dir docs/conformance/v0.9.2
```

- [ ] Run the self-managed leg at the same pushed commit: dispatch `live-lab.yml` on that ref, require the `traditional` job to pass its gate, and copy the `live-lab-public` artifact's report into `docs/conformance/v0.9.2/`.
- [ ] Read each report. Require three reports with thirteen `pass` entries each. A `fail` on the new contract with clean cleanup goes to Task 3, then that flavor's leg is rerun with `--flavors <name>`. A cleanup, harness, or baseline failure blocks further mutation on that target until diagnosed.
- [ ] If a trial target is unavailable, keep that measurement open in `docs/reviews/v0.9.2.md`. Do not stop the Hosted deployment.
- [ ] Confirm the CI teardown step succeeded. Record the source commit, the CI run, the UTC time, the measured versions, and the protocol path of each child for Task 6.

## Task 5: Run the two-client consent matrix

Integrator only, on the Hosted test deployment (D35), after Task 4. Follow
[design section 9.3](../specs/elasticctl-mcp-mutation-design/09-testing-and-evidence.md#93-real-clients).

Setup:

- [ ] Build the binary at the Task 4 source commit. Read-only preflight: Hosted answers `elkctl info` and holds zero marker objects apart from closed marker alerts. Import one disabled marker rule through the CLI. Write the scratch MCP configuration for the built binary with the Hosted profile and `--allow-mutations rules-toggle,cases`, wrapped in `scripts/mcp-stdio-shim.sh` from 0.8.2.
- [ ] Record client versions and the OS.

Claude Code, in an interactive session inside a terminal multiplexer, with
the scratch configuration and `--strict-mcp-config`:

- [ ] Accept, decline, and dismiss (Esc) on the current path. For each: the pane shows the permission card and the form, with the rule's `rule_id` and the credential note readable in full; the shim shows `input_required`, then the retry with `inputResponses` and `requestState`; the marker rule changes only on accept.
- [ ] The same three with `MCP_PROTOCOL_NEGOTIATION=legacy`: the shim shows the server-sent `elicitation/create` and its answer.
- [ ] `claude -p` asking for the change: no change. Record whether `plan_apply` reached the server and which elicitation action, if any, the shim shows (M12).
- [ ] A session in `bypassPermissions`: the permission card for `plan_apply` still appears; no change without a person.
- [ ] A session with an allow rule for the `plan_apply` tool: the card still appears and the form still appears.
- [ ] A session with a scratch `Elicitation` hook that returns `accept` and `apply: true`: record whether the card appears and whether the plan applies. Remove the hook file afterward.
- [ ] A prompt that tells the model to enable the rule without asking anyone: record every call the model made. Pass means no call applied without the card and the form.

Codex CLI, in an interactive session with an inline
`-c mcp_servers.elasticctl.*` override:

- [ ] Accept, decline, and dismiss on the legacy path. Record the negotiated protocol, the approval prompt for `plan_apply`, and the form.
- [ ] `codex exec` asking for the change: no change; record the elicitation action.
- [ ] `approval_policy = "never"` with full access: the form is declined and nothing changes.
- [ ] `mcp_servers.elasticctl.tools.plan_apply.approval_mode = "approve"`: the form still appears; nothing changes without it.
- [ ] The same model-pressure prompt as for Claude Code.
- [ ] If the `mcp_2026_07_28` feature can be enabled in the installed version, repeat Accept on the current path and record it as extra evidence. If it cannot, record that.

Close:

- [ ] A client-observed defect goes to Task 3. A client that cannot run is an evidence gap in the findings, never a pass from its documents.
- [ ] Remove the marker rule with `elkctl rules delete <rule_id> --yes` and each case the runs created with `elkctl cases delete <id> --yes`, taking the ids from the private shim logs. Rerun the preflight. Confirm the scratch directory holds every client file that was created.

## Release gates

1. Three matrix reports with thirteen passes each, from one source commit.
2. For Claude Code: accept, decline, and dismiss on both protocol paths, the
   non-interactive refusal, the skipped-prompt mode, the allow rule, and the
   model-pressure prompt all end with no unconfirmed change.
3. For Codex CLI: accept, decline, and dismiss on the legacy path, the
   non-interactive refusal, the `never` mode, the `approve` mode, and the
   model-pressure prompt all end with no unconfirmed change.
4. The hook row is recorded.
5. Every confirmed defect has a regression and a reviewed fix, and the live
   and client runs it invalidated were repeated.
6. All gate commands pass on the release commit.
