# elasticctl 0.9.0 MCP Plan-and-Confirm Foundation Implementation Plan

Steps use checkbox (`- [ ]`) syntax. Mark a step done only with its evidence.

**Goal:** Ship the consent mechanism for MCP mutation and one class,
`rules-toggle`, behind `mcp serve --allow-mutations`. Land every `-api`
addition 0.9 needs and run every live measurement while stacks are available.

**Architecture:** Planners read through `-api` and store a plan in `-mcp`
memory. `plan_apply` asks the client for a form answer on the elicitation
channel, re-checks the stack, and sends one write on a one-attempt transport.
The CLI passes a class list and changes nothing else.

**Tech Stack:** Rust 2024, Rust 1.97.1, Tokio, serde, rmcp 3.9.0 with
`server`, `macros`, `transport-io`, and `elicitation`; `sha2`, `getrandom`;
wiremock, assert_cmd, insta, jsonschema.

**Spec:** [MCP mutation design](../specs/elasticctl-mcp-mutation-design.md),
sections 1 to 11. [Research](v0.9-research.md) holds the evidence and the
measurement list M1 to M12.

Status: Tasks 2 to 5 are done on `dev-0.9` (2026-11-10). Tasks 1 and 6 to 14 wait for the 0.8.2 release; `dev-0.9` merges into `master` after v0.8.2 is tagged.

## Global Constraints

- Without `--allow-mutations` the catalog, every schema, every result, and
  the server instructions equal the released 0.8.2 server, byte for byte.
- Only `rules-toggle` is a valid class in this version. Other class names are
  a usage error.
- `plan_apply` has one input, `plan_id`. No argument, tool result, resource,
  or prompt confirms. Confirmation is read only from an elicitation answer.
- Every apply is one write request on a transport with one HTTP attempt, no
  redirects, and no connection pool. Planners and checks send no PUT, PATCH, DELETE, or mutating
  POST.
- Limits: 8 open plans, 32 final records, 900 second life, 20 objects per
  plan, 262,144 byte plan body, 8,192 byte consent text, 3 prompts per plan,
  240 second legacy wait, 1 waiting legacy confirmation. The 0.7 limits stay.
- No existing `-api` signature, request body, or error text changes. CLI
  output is byte-identical with three exceptions: the `mcp` description, the
  new flag in help and the command tree, and the case status conflict error,
  which gains `"http_status": 409`.
- No `clap` type enters `-mcp`, `-api`, or `-core`. `-mcp` does not depend on
  the CLI crate. `-core` gains one opt-in field,
  `TransportOptions::disable_connection_pool`; every existing constructor and
  transport keeps its behavior.
- `--allow-mutations` with a profile that has no `es_url` fails at startup.
- A file that 0.7.5, 0.8, and 0.9 all edit has one owner task here, and that
  task starts only after the earlier edits are merged
  ([design section 10](../specs/elasticctl-mcp-mutation-design/10-dependencies-on-0-8.md#shared-files-and-order-of-work)).
- Errors and audit lines hold static text, ids, counts, and classifications.
  They never hold names, titles, tags, messages, rule bodies, usernames, key
  ids, URLs, or stack error text.
- Fixture files are recorded evidence and are never edited. 0.9 adds no
  request shape and records no fixture.
- Live objects carry the `elasticctl-sample` marker. Every live run verifies
  the baseline before and after. Model-driven clients run only on a
  test-only target: the lab or the Hosted test deployment (design 9.3, D35).
- Local builds use two jobs, tests use four threads, and one build-heavy
  process runs at a time.
- Keep development versions at the released 0.8.2 value. Release preparation
  performs the coordinated bump.

the current `tokio::time::Instant`: insert (refuses the ninth open plan), get
(applies expiry), issue a prompt (counts it, optionally makes a handle, closes
the plan as `declined` on the fourth), take a handle (single use), begin
apply (`open` to `applying` once), finish (`applied`, `failed`, `unknown`,
or `stale` from `applying`), close (`declined`, `stale`, `discarded` from
`open`), and list. Final records beyond 32
drop oldest first. `view.rs` builds the plan view and the list rows of
[design section 8.4](../specs/elasticctl-mcp-mutation-design/08-apply-errors-and-cancellation.md#84-results-and-audit-trail).
`audit.rs` builds each audit line as a JSON string and hands it to a sink
held by `ServerState`; production writes it to stderr with the startup
diagnostics writer.
