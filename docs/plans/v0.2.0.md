# elasticctl 0.2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Complete the detection-rules vertical — exception lists as managed
objects, prebuilt rule status and installation, `--source` scoping — and move
all command orchestration into `-api` first, so none of it is written twice.

**Architecture:** Six waves. Wave 1 moves orchestration out of `cli/src/cmd/`
into `-api` behind typed structs, guarded by snapshot tests that prove rendered
output does not change. Wave 2 fixes identity and the codec. Wave 3 builds the
exceptions vertical on that base. Wave 4 adds prebuilt rules and `--source`.
Wave 5 fixes correctness and failure-recovery gaps found in the completed
vertical. Wave 6 records fixtures, runs live conformance, writes release
metadata, and completes the release preflight.

**Tech Stack:** Rust 2024 stable, `clap` v4 derive, `reqwest`/`rustls`/`tokio`,
`serde_json`, `serde_yaml_ng`, `thiserror`; tests use `wiremock`, `assert_cmd`,
`tempfile`, and `insta` (added in Task 1).

**Spec:** `docs/specs/elasticctl-design.md`. The plan argues from the spec.
Where they disagree, **the spec wins and this plan is wrong** — fix the plan.

## Global Constraints

Copied from the spec. Every task's requirements implicitly include this list.

- Dependency direction is one way: `elasticctl-cli` → `elasticctl-api` →
  `elasticctl-core`. `xtask` may use `-api` and `-core`, never `-cli`.
- **Command functions return typed values and never print.** Rendering belongs
  to `elasticctl-cli::render`.
- **Orchestration belongs in `-api`, returning typed structs.** `cli/cmd/`
  parses arguments, calls one API function, hands the result to render. The two
  deliberate exceptions are `cmd/meta.rs` (reflects the `clap` tree) and
  `cmd/config_cmd.rs` (manages the operator's local profile file).
- **`clap` types never appear in `-api` or `-core`.** Pass values, not parsed
  arg structs.
- Rule identity is **always `rule_id`**. Exception list identity is **always
  `list_id` plus `namespace_type`**. Never the volatile saved-object `id`.
- Every remote mutation is a dry run by default; `--yes` applies. Preview and
  apply both print a banner naming profile, host, and space.
- `state push` never deletes remote rules or exception list containers.
  Exception *items* inside a mirrored container reconcile exactly (spec 5.4).
- Never put credentials in URLs. Debug logs complete URLs, but exclude
  authorization headers and bodies.
- `kbn-xsrf: true` on every non-GET Kibana request.
  `elastic-api-version: 2023-10-31` on versioned public APIs. It must be a date
  string; `1` and `2` are rejected.
- No task asserts an unmeasured API shape. Section 2 below lists what was
  measured, when, and what was not.
- Fixtures are recorded, never hand-written or hand-edited. Re-record instead.
  Scope every recording to sample objects; fixtures are public.
- Package names: `elasticctl-core`, `elasticctl-api`, `elasticctl` (the binary
  crate, in `crates/elasticctl-cli`). `-p elasticctl-cli` does not resolve.
- Gates, all must pass before any commit lands:
  `cargo test`, `cargo fmt --all --check`,
  `cargo clippy --workspace --all-targets -- -D warnings`.

## 1. What this release does not do

- **No per-rule prebuilt upgrade.** The only route offering it is
  `access: 'internal'`. Spec 4.6.
- **No value-list content management.** Spec 4.6 and 7.7. `doctor` reports
  whether the data streams exist; `push` reports a referenced value list that
  is absent. Nothing creates or mirrors value-list items.
- **No `exceptions create` and no `exceptions attach`/`detach`.** Spec 4.
- **No endpoint exception list (`/api/endpoint_list`) support.** It has its own
  routes and its own lifecycle, and no rule references it through
  `exceptions_list`. Out of scope, not forgotten.

**`apply_push` takes no `dir`, and this is load-bearing.** The plan originally
passed one, which forced a second `read_local` *after* `-cli` had blocked on a
TTY prompt for an unbounded time: the operator confirms a change computed from
the file on disk at plan time, and a different file gets pushed, with no
re-preview and nothing detecting the swap. Spec 6.1 says every remote mutation
previews before it applies; a preview the apply can diverge from is not that
preview. `plan_push` resolves the desired rules once and `PushPlan` carries
them, which also removes a second full parse of the mirror — 2,066 rules on the
dev project.

`plan_push` takes the stack identity as three plain values rather than leaving
`ChangeReport.profile`/`host`/`space` empty for the caller to remember to fill.
They are values, not `Context` and not `clap` types, so passing them keeps the
architecture rule intact while making the change-evidence report correct by
construction. A change ticket that silently records `"profile": ""` is worse
than one that fails to write.

`push` splits into `plan_push` and `apply_push` because the guard sits between
them and the guard is a `-cli` concern — it reads a TTY and prints a banner.
`-api` must not do either. `plan_push` returns everything the banner needs;
`-cli` decides; `apply_push` performs. A caller that never calls `apply_push`
has performed a dry run, which is what makes the dry-run default structural
rather than a flag someone can forget.

```rust
enum Line { Rule, List, Item, Trailer }

/// Classify one NDJSON line from an export bundle.
///
/// Order matters. An exception item carries both `item_id` and `list_id`, so
/// the item test must precede the list test. A trailer carries neither an id
/// nor a `list_id`, and the two export routes emit different counters:
/// rules export writes `exported_count`, exception export writes
/// `exported_exception_list_count` and no `exported_count` (measured fact 7).
fn classify(v: &Value) -> Option<Line> {
    // `rule_id` first, then `item_id`, then `list_id`. On every measured shape
    // rule-vs-item order is arbitrary — no rule carries a top-level `item_id`
    // and no item carries `rule_id` — so pick the order that fails loudly if
    // that ever stops being true. A rule misfiled as an item vanishes from
    // `decode_ndjson` silently; an item misfiled as a rule is rejected by
    // `Rule::from_value` with a line number.
    if v.get("rule_id").is_some() {
        return Some(Line::Rule);
    }
    if v.get("item_id").is_some() {
        return Some(Line::Item);
    }
    if v.get("list_id").is_some() {
        return Some(Line::List);
    }
    if v.get("exported_count").is_some() || v.get("exported_exception_list_count").is_some() {
        return Some(Line::Trailer);
    }
    None
}

pub fn decode_bundle(body: &str) -> Result<Bundle> {
    let mut out = Bundle::default();
    for (i, line) in body.lines().enumerate() {
        let line = line.trim();
        if line.is_empty() {
            continue;
        }
        let value: Value = serde_json::from_str(line).map_err(|e| {
            Error::new(ErrorKind::Error, format!("invalid JSON on line {}: {e}", i + 1))
        })?;
        let at = |e: Error| Error::new(ErrorKind::Error, format!("line {}: {}", i + 1, e.message));
        match classify(&value) {
            Some(Line::Rule) => out.rules.push(Rule::from_value(value).map_err(at)?),
            Some(Line::List) => out.lists.push(ExceptionList::from_value(value).map_err(at)?),
            Some(Line::Item) => out.items.push(ExceptionItem::from_value(value).map_err(at)?),
            Some(Line::Trailer) => out.summary = serde_json::from_value(value).ok(),
            None => {
                return Err(Error::new(
                    ErrorKind::Error,
                    format!(
                        "line {}: not a rule, exception list, exception item, or export trailer",
                        i + 1
                    ),
                ));
            }
        }
    }
    Ok(out)
}
```

`encode_bundle` writes rules, then lists, then items, with no trailer — the
same order the server emits and the order `_import` needs.

**`rules export` must emit the whole bundle.** Fixing the decoder alone leaves
the command worse than it ships: measured on 2026-08-14, 0.1.3 fails loudly with
`line 2: a rule must have a rule_id`, while a decoder-only fix makes
`export_rules` return one line where the server sent four, dropping the
exception list and its items with no signal. A file like that imports into
another stack as a rule referencing a list that does not exist there. Spec 5.2
names the principle: silent truncation is the one outcome worse than failing,
and spec 6.2 already requires export's stdout to be the rule file emitted
verbatim.

So `export_rules` decodes the bundle, normalizes the rules, and re-encodes the
bundle — not just its rules. For a corpus with no exception lists the two are
identical, so existing export output does not move.

The same rule applies to `--format-file yaml`, which cannot represent a bundle:
its document is a sequence of rules, and `decode_yaml` reads one back. Rather
than invent a YAML bundle shape nobody has asked for, a YAML export whose bundle
carries exception content is **refused**, with an error naming
`--format-file ndjson`. A YAML export of rules without exceptions is unchanged.
That keeps the same principle as the NDJSON path — fail loudly rather than
truncate quietly — without committing to a second on-disk format. Spec 5.4's
mirror is unaffected: it writes exception lists to their own files under
`config/exceptions/`, which is a different question from what one export
document can hold.

`decode_ndjson` becomes:

```rust
pub fn decode_ndjson(body: &str) -> Result<(Vec<Rule>, Option<ExportSummary>)> {
    let b = decode_bundle(body)?;
    Ok((b.rules, b.summary))
}
```

/// Spec 4.5. Compare each remote rule's stored pointer against the live
/// container for its `list_id`. `comparable` has stripped this field by the
/// time `Drift::compute` runs, so the check works on the raw response.
fn dangling_pointers(
    raw_remote: &[Rule],
    live: &BTreeMap<ListKey, String>,
) -> Vec<DanglingPointer> {
    let mut out = Vec::new();
    for rule in raw_remote {
        let Ok(rule_id) = rule.rule_id() else { continue };
        for r in model::exception_refs(rule) {
            let key = ListKey {
                list_id: r.list_id.clone(),
                namespace_type: r.namespace_type.clone(),
            };
            let live_id = live.get(&key).cloned();
            let stored = r.id.clone();
            if live_id.as_deref() != stored.as_deref() {
                out.push(DanglingPointer {
                    rule_id: rule_id.to_string(),
                    list_id: r.list_id,
                    stored_id: stored.map(Value::String).unwrap_or(Value::Null),
                    live_id,
                });
            }
        }
    }
    out
}

The fixed journal root is `<mirror>/.elasticctl-pull-txn/`. Its manifest lists
every planned relative path, whether that path existed, and its durable phase.
Staged bytes and backups stay on the mirror filesystem.

The journal is append-only NDJSON. Its first synced record contains the full
`Prepared` entry set. Each later synced record contains one entry index and its
next phase. Recovery replays complete newline-terminated records and ignores
only a final incomplete line, so a crash cannot leave a truncated rewritten
manifest as the sole recovery evidence.

`acquire_pull` uses a sibling lock at
`<mirror-parent>/.<mirror-name>.elasticctl-pull.lock`. It must not create
`<mirror>` or `.elasticctl-pull-txn`. Validate the mirror parent and acquire
this exclusive standard-library file lock before recovery. Hold it for the
whole pull, including recovery, remote reads, and commit. A second process
fails before it can mistake an active transaction for a crashed one. Validate
every `StagedFile.relative`: it must start with `rules/` or `exceptions/` and
contain no root, prefix, or parent component.

- [ ] **Step 2: Implement the recoverable transaction**

`replace_staged_files` then:

1. writes and syncs every staged file;
2. writes and syncs the complete `Prepared` record before the first target
   change;
3. appends and syncs `BackingUp`, renames an existing target to backup, then
   appends and syncs `BackedUp`;
4. appends and syncs `Installing`, renames the staged file to the absent target,
   then appends and syncs `Installed`;
5. removes the transaction only after every replacement succeeds.

rename. It restores a backup only when it exists; otherwise it preserves the
old target. For a path that did not exist before, recovery examines both target
and staged paths. In `Installing` or `Installed`, if the staged path is absent
and the target exists, remove that transaction-owned target; if the staged path
remains, leave the absent target untouched. Run this rule before removing the
transaction directory. On a returned error, restore every manifest entry. If
rollback also fails or the process stops, preserve the journal and backups; the
next pull recovers them before doing network work.
